# 可选工具区（tools\）

> **按需拉动，不进接手路径**：AI 接手工作时无需读取本目录。
> 只有出现具体需求（可视化 / 定时 / 报告）时才读对应规范。
>
> **本目录只放"规范"，不放实现**——实现能力由各平台原生提供，不随技能包分发。
> 随包分发的**可执行实现**在 `scripts\`（协议门禁），两者的分工不要混淆。

---

## 一、本目录内容

| 目录 | 用途 | 何时读 |
|---|---|---|
| `visualize\` | 可视化规范：把结构关系画成图（平台无关） | 需要图示表达依赖 / 流程 / 组织时 |
| `schedule\` | 定时任务规范：提醒 / 周期检查 / 定期汇报 | 需要定时能力时 |
| `report\` | 报告生成规范：日报 / 周报取数口径 | 需要成体系报告时 |

**三者都只有 `README.md`，没有代码。** 这是刻意的：

- 定时与可视化**强依赖平台**（cron / Task Scheduler / 图表库各不相同），打包实现等于绑定平台；
- 报告取数口径**必须与本项目实际的 INDEX / STATE 字段对齐**，无法预置。

---

## 二、与 `scripts\` 的分工（易混淆，务必分清）

| | `scripts\` | `tools\` |
|---|---|---|
| 性质 | 可执行实现（确定性函数） | 规范文档（指导性） |
| 是否随包分发 | **是** | 是（仅文档） |
| 是否阻塞 | **是**，退出码 0/1/2/3 参与门禁 | 否，仅供参考 |
| 判定 | 机器判定，无歧义 | 人/模型判断 |
| 典型内容 | 提交门禁、索引完整性、三方对账、代码度量 | 画图、定时、写报告 |

> 一句话：**能确定性判定的都进了 `scripts\`；剩下的是"怎么表达"的问题，留在 `tools\`。**
> **本目录只放规范，不放实现**：能确定性判定的检查一律进 `scripts\`（有退出码、可进 CI、可阻塞提交）；
> 「怎么表达」类问题（画图、定时、写报告）才留在这里。

---

## 三、防失控规则

1. **按需拉动**：需要时才读对应规范，不提前加载。
2. **不进接手路径**：工具规范不属于"接手三件事"。
3. **只放规范不放平台实现**：协议登记，实现靠平台原生能力。

---

## 四、调用方式

- **直接调用**：管理者在任意会话（含新会话、已暂停的会话）直接说「生成周报 / 画依赖图 / 检查记录」，
  AI 读对应规范并执行，**无需先浏览目录**。
- **上下文独立**：调用工具只读工作区文件，不打断其他正在工作的会话。
- **与「查看项目」的区别**：查看项目是「浏览目录 → 发现工具 → 才决定」；
  调用工具是「已知要哪个工具 → 直接调用」。

---

## 五、扩展

新增工具时：在 `tools\` 下新增子目录 + `README.md` 规范文件，并在本 README 登记。

**不得新增**以下两类：

- **平台原生就能做到的**（搜索 / 翻译 / 写作 / 纪要转写 / 问答）——其产出按现有协议自然沉淀即可；
- **确定性可判定的检查**——那属于 `scripts\`，应有退出码、应进 CI、应能阻塞提交。
