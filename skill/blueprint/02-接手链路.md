# 第 2 页 · 接手链路

> 这一页回答：**接手一项工作到底读什么、读多少、凭什么不增长。**

---

## 一、指针链（承重墙）

```
任务卡「上次交接」 ──▶ reports/ 一篇交接记录 ──▶ 索引 [接力] 行
```

- 记录只写**本任务需要的信息**：不贴 diff、不复制代码。
- 索引行是**入口**，不是内容：它保证「这个编号的活在哪一篇记录里」永远可查。
- 链条上任一环节断了 → 走 `references/recovery.md`（补全 / 重连 / 标「数据待补」，**禁止伪造**）。

## 二、接手只做三件事

```
① 读任务卡        tasks/<卡>.md             定位工作，不漫读全项目
② 沿指针读一篇    reports/<卡上指向的那篇>   不够用才多读
③ 需要全局判断时  STATE.md / MAP.md          首次接手 / 跨模块 / 整体审视
```

**读完即写回**：把增量写进卡的「要点 / 已提炼」，保证**每篇记录最多被读一次**。

## 三、成本口径：单位是字符，不是文件数

口径「一份卡 + 一篇记录」描述的是**读哪些**，不是**读多少**。实测某真实项目：

| 项 | 实测 |
|---|---|
| 单张任务卡 | 中位 5,445 字符 · 最大 22,002 |
| 指针记录（一篇） | 中位 3,505 字符 |
| 接手最小集（卡 + 记录） | 中位 ≈ 8,900 字符 |

**文件数恒定 ≠ 成本恒定**：一份 22,002 字符的卡，就是 5,445 字符那份的 4 倍。
**读进来的东西会留在上下文里**，跟着整场对话一起付费——所以量的是字符。

## 四、容量上限（都是上限，不是可扩容量）

| 封顶 | 管什么 |
|---|---|
| `capacity.state_max_chars` | STATE 快照字数 |
| `capacity.index_hot_rows` | 索引热区行数 |
| `capacity.report_archive_threshold` | reports 归档触发篇数 |
| `capacity.card_max_chars` | 单张任务卡字数（卡是定位与指针，不是档案） |
| `capacity.onboarding_max_chars` | 接手包（卡 + 指针记录）字数 |
| `capacity.reviews_hot_lines` | 留痕尾部行数 |
| `capacity.blueprint_max_lines` · `blueprint_max_para_chars` | 设计蓝图长度与段落 |

**不得以「更完整 / 更全面」为由调大**——这是容量上限的意义所在。
量尺由 `scripts/overview.py` 的「接手包」一行给出；超限时就地给出下一步（写回 / 归档 / 移写）。

## 五、超限了怎么办

| 超的是什么 | 动作 |
|---|---|
| 卡太长 | 把过程细节**写回** `reports/`，卡上只留指针与当前落点 |
| STATE 太长 | 按快照纪律把历史段移入 `reports/`，只留当前快照 |
| 索引热区满 | `closeout.py index-add` 自动移行（只移 [完成]/[废弃]，**[接力] 行留驻**） |
| reports 过多 | `closeout.py archive-reports` 滚动归档并同步索引指向 |
| 留痕过长 | `closeout.py reviews-archive` 滚入 `archives/REVIEWS_archived.md` |
