# 项目管理AI轻量化接力（技能入口）

> **定位**：通用型项目管理技能，不为特定项目服务。核心哲学——项目可以复杂沉重，AI 接手只读所需：负担不随项目规模增长。
> **本质目标（跨阻碍）**：跨越平台、AI、时间、项目等阻碍，让接手 AI 以更小读取代价理解工作需求、降低出错率。
> **存量项目（已开工无管理结构）**：先读 `LEGACY_ONBOARDING.md`（轻量登记 + 渐进整理，不深度整理历史）。

---

## 一、触发时机

1. **新项目开工前**：初始化协同工作区（创建管理目录 + 填写初始信息）
2. **长期未动项目接手前**：按需读取工作文件（任务卡驱动，不重复读本技能）
3. **存量项目接入**（已开工、无管理结构）：读 `LEGACY_ONBOARDING.md` 执行接入

## 二、使用流程

```
① 确认工作区根 {WORKSPACE_ROOT}（用户选择一次：默认或自定义；管理目录子文件夹技能自动创建）
② 创建管理目录（通用第一步，任何项目都要）：
   MAP.md / STATE.md / REVIEWS.md / tasks\ / reports\ / INDEX.md / archives\（含 done\、INDEX_archived.md）/ tools\
③ 填写初始信息：MAP 占位符替换（环境/规则/协议/路径注册表，含 [技能源包路径]、[备份方式]、[裁决者]、稳定 ID、并发元数据与三种模式）
④ 登记首条任务卡（tasks\，按工作命名）
⑤ 运行（此后不再重复读技能，只按工作文件运行）：
   读任务卡 → 干活 → 收工分流（覆盖式更新/移卡）→ INDEX 登记
   （tasks\ 为空时按用户指令新建卡；无卡 = 当前无活）
   （多卡时：用户指定任务 → 去 tasks\ 找同名/相近名卡；多卡同名时问用户确认）
```

## 三、核心协议

### 3.1 协议速查表

| 协议 | 内容 |
|---|---|
| 任务卡驱动接手 | 读对应任务卡（描述/要点/涉及/代码根路径）→ 开工前在卡「承接」认领 → 够用直接开工；不够沿「上次交接」读 reports；**卡尾含「收工协议速记」**（收工义务随卡分发，接手即见——不依赖重读技能，防只看卡干活漏协议义务） |
| 收工分流 | **未完成 → 必须建卡**（包括尚未建卡、只在当前对话里的工作）；有下一步 → 完整交接 + 覆盖式更新任务卡；无下一步 → 简化总结 + **移卡到 archives\done\**（不删卡，保留完成记录）；**收工门禁失败则阻塞完成**，不得声称完成；四件套：交接 → 卡更新/移卡 → INDEX → STATE（条目级写） |
| 进度锚点 | 工作中**落点即覆盖**写卡上「进度锚点」行（单行、只写自己认领的卡）——断网/断电/断 token 等中断来不及收工时，卡上自然留下最新落点，下一位沿锚点 + 实际文件状态（git status）续作；正常收工时内容沉淀进要点/交接后清「—」——**交接格式零变化**；任务取消的卡锚点保留原样归档（可追溯） |
| 下一步判断标准 | 有下一步 = 用户还要继续 / 活没做完 / 有遗留问题；无下一步 = 用户明确说"做完了" / 活全清 |
| 覆盖式更新 | 任务卡/STATE 永远覆盖为最新，不追加、不滚雪球；历史归 reports + INDEX；STATE 并行收工时按条目更新（见 3.2） |
| 提炼回卡 | 读 reports 后提炼增量覆盖回卡 → 每篇 reports 最多被读一次 |
| INDEX 登记 | 每次收工加一行（日期 + 类型 + 一句话摘要 + 详见 reports\xxx.md）；**[接力]** 沿链读 / **[完成]** 审视读 / **[废弃]** 留痕防误做 |
| 人读区与 AI 区 | 人读区（3 行摘要）由 AI 区自动生成——任务←描述首句、状态←状态字段、下一步←要点①，覆盖更新时同步重写，不靠主观对齐 |
| 最小交接 | 6 块 + 第 7 块「任务卡更新」（有对应任务卡时必填） |
| 档案红线 | **禁止删除/移动 reports\ 与 archives\ 下任何文件**——唯一例外 = 收工归档流程（超阈值滚动归档、完成移卡），移后必须同步 INDEX 对应行指向；改动记录三层：**MAP 记结构**（新路径/新分支）、**reports 记摘要**（工程有 git 时「改动点」每条附 commit hash——需要完整 diff 时 git show 即得）、**INDEX 记指针行**（双写永不丢） |
| 命名规范 | reports `YYYY-MM-DD_主题_AI标识.md`（AI 标识含短码：`{平台}-{AI名}-{短码}`，短码 2~4 位随机；写前先 list 目录确认无同名）；任务卡按工作命名 |
| 元管理分流 | 技能自身事务（REVIEWS 复盘、版本漂移检测、恢复动作登记）一律追加写工作区 `REVIEWS.md`，**不写 reports\、不登 INDEX**——项目 reports/INDEX 只存项目工作记录 |
| 并发写规则 | 摘要：写前读 · revision/hash · 原子写或 compare-and-swap · 写后验 · STATE 条目级写 · 单写者责任 · 冲突文件交管理者（**细则见 3.2**） |
| 缺失补全 | 摘要：技能源包为权威源，缺失/过时从源包复制实例化；恢复保存 RAW-SHA256/NORMALIZED-SHA256、编码和候选源证明，恢复不出标「数据待补」不伪造（**细则见 3.3**） |

### 3.2 并发写规则（细则）

写前读（覆盖写 STATE/任务卡、追加写 INDEX 前先读最新）· 每次写记录 `revision`、规范化内容的 SHA-256 和写者 ID · 优先临时文件 + 原子 rename；不具备原子 rename 时使用 compare-and-swap（提交前再次比对 revision/hash）· 写后验（重读并核对 revision/hash）· **单写者责任**：每个文件同一时刻只能有一个声明的 owner，其他 AI 只能生成冲突文件 `CONFLICT_<ID>_<timestamp>.md`，不得覆盖· **STATE 条目级写**（只更新自己任务条目和人读区，其余原样保留）· 冲突交管理者，时间戳仅辅证。

### 3.3 缺失补全（细则）

技能源包为权威源：项目工作区技能文件缺失或过时（源包版本更高）→ 从源包复制模板实例化重填。恢复每个候选源都记录路径、读取时间、编码、RAW-SHA256（原始字节）与 NORMALIZED-SHA256（统一 UTF-8、换行和 BOM 后），并保留候选源证明；无法证明的字段标「数据待补」，不伪造。任何恢复动作顺手记一行 **REVIEWS.md**（元管理分流，不进 reports/INDEX）。

### 3.5 稳定标识、设计生命周期与权限

- `TASK-ID`：`TASK-YYYYMMDD-<6位大写 base32>`，任务卡创建后永久不变；文件名可改，引用只能用 ID。
- `EVENT-ID`：`EVT-YYYYMMDD-<8位大写 base32>`，每次交接、归档、恢复、冲突和批准事件唯一；重试也产生新 ID。
- `DESIGN-ID`：`DSN-YYYYMMDD-<6位大写 base32>`，设计卡唯一；草案 → 评审中 → 已批准/已拒绝/已废弃。只有 `已批准` 设计卡才能生成执行任务卡，并在执行卡中回链 DESIGN-ID；批准、拒绝和废弃均写 EVENT-ID。

| 角色 | 允许 | 禁止 |
|---|---|---|
| 执行 AI | 认领自己的 TASK-ID、写自己的 reports/STATE 条目、提出设计卡 | 批准设计、覆盖他人 owner 文件、删除/移动档案 |
| 审计 AI | 只读检查、生成 [问题]/[待核] 报告 | 修改业务记录、替代管理者裁决 |
| 管理者/裁决者 | 批准设计、分配 owner、裁决冲突/废弃、执行归档 | 无凭证改写历史 |
| 恢复 AI | 只读生成候选与证明、经确认写恢复草稿 | 无确认覆盖正式文件 |

### 3.6 模式、归档与一致性协议

| 模式 | 文件集 | 角色与检查 | 升级 |
|---|---|---|---|
| light | TASK 卡、INDEX、archives\INDEX_archived.md | 执行 AI；ID/路径/收工门禁 | 出现并行任务、设计批准或冲突时升 standard |
| standard | light + MAP、STATE、reports、REVIEWS | 执行 AI + 审计 AI；四件套、STATE 条目级写、版本/归档检查 | 需要多人协作、跨分支或设计评审时升 coordination |
| coordination | standard + 设计卡、冲突文件、权限/事件证明 | 管理者分配 owner；CAS/原子写、冲突审计、批准门禁 | 风险下降且管理者明确批准后可降级，历史不回写 |

`INDEX.md` 是近期指针，`archives\INDEX_archived.md` 是不可变历史总账：每个 EVENT-ID 只能追加一次；主文件超 N 行时按日期从旧到新移动到归档，同时保留原 EVENT-ID、原路径和移动事件。归档算法必须先写归档临时文件并校验 hash，再原子替换归档文件，最后 CAS 更新主文件；任一步失败则保留原主文件、留下 `CONFLICT_*.md` 和 REVIEWS 事件，不得宣称完成。完成卡仅从 `tasks\` 移入 `archives\done\`，不覆盖同名目标。

### 3.7 边界声明

本包定义协议、模板和脚本**生成规范**；不实现或默认启用运行时守护进程、自动归档器、权限系统或持续监督。平台脚本只能按 `SCRIPT_SPEC.md` 生成并由用户确认落地。

### 3.4 术语表（保留术语 · 白话对照）

| 术语 | 白话 |
|---|---|
| 任务卡驱动 | 接手先读对应任务卡定位工作，不漫读全项目 |
| 收工分流 | 收工时按"有没有下一步"分流：有 → 完整交接；无 → 简化总结 + 移卡归档 |
| 收工四件套 | 每次收工必做的四件事：交接 reports → 卡更新/移卡 → INDEX 登记 → STATE 更新 |
| 覆盖式更新 | 文件永远覆盖为最新内容，不追加历史；历史归 reports/INDEX |
| 最小交接 | 交接只写本任务需要的信息，不贴 diff、不复制代码 |
| 提炼回卡 | 读过 reports 后把增量信息写回任务卡要点，保证每篇 reports 最多被读一次 |
| 元管理分流 | 技能自身的事务记 REVIEWS.md，与项目工作记录（reports/INDEX）分开存放 |
| 条目级写 | 并行收工时 STATE 只更新自己任务的条目，禁止整文件盲覆盖 |
| 并发写规则 | 多 AI 同时写文件时的纪律：写前读最新、写后读回确认、冲突按规则裁决 |
| 先查重 | 建管理目录前先探测是否已存在该项目实例，有则归并、禁止另起 |
| 轻量登记 | 存量项目接入时只登记当前可见信息，不做历史深挖 |
| 渐进整理 | 历史在后续工作中边做边归类，按需补录 |
| 物理隔离 | 管理目录建在工程代码之外，不混入源码树 |
| 锚点 | 指向具体文件/记录的引用路径（如「上次交接」指向某篇 reports） |
| 双写 | INDEX 同时写主文件与归档文件两处，行永不丢失 |

> **旧名对照**（存量工作区升级用）：最后折叠 → 已提炼 · 工程锚点 → 代码根路径 · 技能资产层（资产层）→ 技能源包 · 锚点组 → 已并入「上次交接」说明 · 沉淀再前进 → 提炼回卡 · 即时复制型 → 未建卡的工作 · 落盘接取型 → 已建卡的工作 · 派生视图/机械重写 → 人读区由 AI 区自动生成 · 内容级并发安全 → 并发写规则 · 前置查重 → 先查重 · 树链式 → 按模块/分支分工 · 双阅读层 → 人读区 + AI 区 · 认路总图 → 项目地图（MAP）。

## 六、项目查看视图（人眼查看 · 平台无关约定）

- **入口（管理者三件事）**：① 新建项目 → 引用本技能初始化；② 查看项目 → 查看已有项目（见下）；③ 调用工具 → 直接调用内置工具/已生成脚本（见 tools\README 调用方式）。
- **「查看项目」默认先展示整个目录结构**（工作区目录树：tasks / reports / INDEX / REVIEWS / archives / tools 一眼全貌），人先看全貌、再点进某处；「怎么打开/怎么点」按平台能力自适应。
- **两个查看粒度（区分近期与全量）**：
  - 近期 → 读 `INDEX.md` 主文件（仅最近 N=20 行，默认）
  - 全部历史 → 仅用户明确要看全部时才读 `archives\INDEX_archived.md`（完整记录含归档断点）
- **按目录逐项查看**：
  - 项目总览：项目定位 + 任务分布 + 当前任务 + 近期记录 + 决策点 + 工具区 + 目录指引
  - 工具区：三列表格（工具 / 工具名称 / 工具说明）
  - 全部 reports：读 `reports\` 目录
  - 历史追溯：读 `archives\` 目录
  - 决策点详细：读 STATE 决策点段落
  - 任务卡详细：读对应任务卡文件
  - 元管理详细（技能复盘/恢复记录）：读 `REVIEWS.md`
- **呈现约定**：能打开文件/目录的平台 → 提供「打开」入口；无此能力 → AI 读后以表格/列表输出；无交互选择 → 直接列出全部、由用户口述选择
- **INDEX 行数标注与调整话术**（自 INDEX 模板迁入）：接手 AI 在交接 reports 里标注 INDEX 主文件当前行数——未满配置值只显示数字（如"INDEX 近期 16 行"）；满配置值加"可更改"备注；用户想调整时提醒："当前 INDEX 主文件配置上限 N 行，已写满。如需改为其他行数（如 30/50/100 行），归档文件有完整记录可追溯。确认要改吗？"→ 用户确认 → 改 MAP 配置（归档文件完整记录不受影响，历史追溯不断）。

## 七、维护规范（技能自身迭代）

- **权威源唯一**：`SKILL.md` 为协议**唯一权威源**；`README.md`「协议速览」与 `MAP.template.md`「协议」段为**派生快照**（版本号必须与 SKILL.md 一致）；`BLUEPRINT.md` 只记设计要点、不承载协议细节，**不参与版本同步**
- **改协议流程**：先改 SKILL.md（权威源）→ 同步 README 协议速览 + MAP 协议段 → 三处版本号一致递增，防版本不同步
- **更新改造先过保护区**：任何瘦身/简化/合并/字段改名，先逐条过**第八节「变更保护区」门禁**再动手
- **改进先复盘**：技能改进先记入工作区 REVIEWS.md（阻碍→根因→建议→处置→沉淀进技能），再落地修改
- **落地后同步副本**：技能源包（即 MAP「技能源包路径」指向的本体）→ 各分发副本（安装位置与发布形式由发布方决定，如 .user_skills 安装副本、ZIP 发布包；**无分发副本时仅维护技能源包即可**）；源包版本高于项目工作区版本时提示拉取更新——源包自身的容灾不靠分发副本，靠 MAP「[备份方式]」登记的备份

## 八、变更保护区（更新改造必读 · 重要提示）

> 本节是技能包后续**更新、瘦身、简化、合并、字段改名**时的硬性门禁——目的：防止"改着方便"破坏功能配合、抬升接手成本。任何更新改造先逐条过本节，再动手。

### A. 改造门禁（更新/瘦身/简化/合并前逐条核对）

1. **功能零损失**：只减重复副本，不减唯一信息——被削减内容的唯一正本必须仍然存在且可定位；找不到正本就保留原文
2. **交叉影响检查**：改/删/简化任何协议内容前，先查它的**消费者**——tools\ 检查点 1~7 与恢复点 1~5、其他协议条款、模板字段对它的引用。**字段名/块名改名必须先 grep 全包列出同步清单**，逐处同步后才动手；局部简化若会断掉与检查/恢复/交接功能的配合，一律不做（环环相扣实例与改动自检见本节 D）
3. **接手成本不升**：接手路径文件（任务卡 → reports ±1 → STATE/MAP → INDEX）只许变薄或等量、**不许净增**；内容指针化时高频规则必须就地可读（指针只兜低频细节）；技能合并仅在共享同一接手路径、不增加协议入口文件数时允许
4. **成本归属三原则（快照 / 总账 / 分层）**：
   - **写路径恒定**：收工路径上的每个字段必须可**机械派生**（本地 list、单行查找、首句截取——闭着眼能填对）；凡需全量盘点、全局扫描、跨目录统计的字段禁止进入收工流程——要费劲才能填对的字段早晚会填错，错数比没有数更害人
   - **快照与总账分工**：STATE = 当前快照，INDEX 归档文件 = 全量总账；累计统计（完成/废弃总数等"期末余额"）归总账**按需查询**，禁止改回高频维护（每次收工更新的计数器）；改动允许把成本从高频路径移向低频路径，**禁止反向**
   - **主文件容量即封顶**：INDEX 主文件行数 N（默认 20）与 STATE 字数上限（默认 15k）是接手 AI 默认阅读成本的**两处封顶装置，不是可扩大的容量**——不得以"更完整 / 更全面 / 看得更全"为由调大默认值或让主文件承载更多历史（如 20 行扩到 50/100 行，看似近期更完善，实为每个接手 AI 加税）；超限时按覆盖式纪律把历史段移入 reports\；要更多历史 → 按需读归档文件，**分层读取结构（主文件=近期 / 归档=全量）不得合并**
5. **权威源流程**：先改 SKILL.md（权威源）→ 同步 README/MAP 派生快照 → 版本一致（见第七节）
6. **改进先复盘**：改造动因与方案先记 REVIEWS.md，再落地

> **冲突即弹窗（强制提醒义务）**：执行改造的 AI 发现拟议改动与上述任一门禁/原则冲突时，必须**主动向用户显式提醒（弹窗/高亮警示）**——写明冲突的是哪条原则、改了会伤哪个功能、负担加在哪，未经用户明确确认**不得执行**；不得静默服从"照做就是"的指令，也不得静默放行绕过门禁。

### B. 承重结构（禁止删除/弱化/改语义——更新时逐项保留）

1. **reports 指针链**：任务卡「上次交接」→ reports「下一步」→ INDEX [接力] 链 +「交接文件」列——接手成本恒定的承重墙
2. **INDEX 双写**：主文件 N 行 + INDEX_archived.md 全量，行永不丢失（移入不删除）
3. **提炼回卡**：每篇 reports 最多读一次、增量回卡——同时是误删容灾层（读过的已回卡）
4. **档案红线**：AI 不删/不移 reports\ 与 archives\（唯一例外 = 收工归档流程，移后同步 INDEX 行指向）
5. **数据诚实边界**：恢复不出标「数据待补」，禁止伪造
6. **审计/恢复依赖清单**：交接 6+1 块名、任务卡稳定 ID/「上次交接」「已提炼」「代码根路径」「涉及」、revision/hash/CAS 元数据、MAP ID 注册与配置（INDEX 主文件行数 / STATE 字数上限 / reports 归档阈值 / AI 定期排查开关 / 协作模式）——这些是检查点与恢复点的**功能接口**，不是协议复述，瘦身刀不落此处
7. **版本权威源与派生快照一致性**（检查点 6 依据）

### C. 记录与恢复保障（运行期，与改造同守）

- **改动记录三层分工**：MAP = 结构账本（新路径/新分支，分支登记有检查点 4 兜底）· reports = 改动摘要账本（git 可用附 commit hash）· INDEX = 指针账本（双写永不丢）——内容准确性源头在 reports
- **MAP 路径注册表对账**：检查点 7 校验注册表路径存在性——手动移动/改名目录后必须更新 MAP，防"地图静默过时"
- **备份方式登记**：MAP 环境段「[备份方式]」（git / 定期复制 / 无）——整目录误删超出协议恢复能力，靠备份兜底；协议登记不打包实现
- **源包对照还原（类财务对账）**：多记录互证，**对的是一致性，不是直接还原信息**——技能源包文件受损/被删 → ① `SKILL.md` 从**任一项目工作区**逐字对照还原（初始化时原样复制进工作区，即正本）；② README/BLUEPRINT/LEGACY/tools 子规范无工作区副本 → 按 MAP「[备份方式]」或分发副本取回，取不回的标注「待补」不伪造；③ 还原后跑检查点 6 校验版本一致、恢复动作记 REVIEWS.md——对账不一致处凭痕迹分析推导，允许部分还原，禁止凭印象补写

### D. 强耦合警示（每次改动必读）

> 本技能**没有孤立的协议行**。很多单项功能表面只占几行，实际是多个功能点的交汇节点——删掉或改写"几行字"，断掉的是别处正在运转的功能链。每次改动先看实例、再过六问，慎之又慎。

**耦合实例（看似几行、实为节点）：**

| 表面看起来 | 实际承载 |
|---|---|
| MAP 规则段配置行（INDEX 行数 / STATE 字数上限 / reports 阈值 / 检查开关 / 协作模式） | INDEX 截断、STATE 封顶、reports 归档、checks 排查开关等功能的运行依据 + 恢复点 5 对账输入 |
| INDEX 头部「行数标注话术」（1 行指针） | 恢复点 5「提示可更改 + 断点指向归档」的行为来源（话术正本在 SKILL 第六节） |
| 任务卡「上次交接」字段（1 行） | 接手链入口 + 检查点 5 锚点存在性校验 + 恢复点 3 断链修复对象 |
| 交接 6+1 块标题（7 行） | 检查点 1 收工门禁的逐块校验对象 |
| STATE「条目级写」（1 行） | 并行收工不冲突的保证 + 检查点 1 STATE✓ 证据 |
| INDEX 编号规则（2 行） | 检查点 4 全部逻辑依据 + [接力] 链跨归档续接 |

**改动前六问（答不全就停下）：**
1. 这几行被 tools\ 哪些检查点/恢复点当作输入或校验对象？
2. 被哪些模板（HANDOVER / TASK_CARD / INDEX / STATE / MAP）当作字段或块名引用？
3. 被哪些派生快照（README / MAP 协议段）与 SKILL 其他行引用？
4. 改后原本依赖它的每个功能，是否仍有**等价路径**完成任务？
5. 接手 AI 会不会因此需要读更多东西（接手成本是否上升）？
6. 同步清单是否齐备、改动记录是否已写 REVIEWS.md？

**纪律**：答不清"谁在消费这几行"就不改；改动**宁小勿断**——宁可多保留一行看似冗余的协议，不可断掉一环正在运转的配合。

### E. 对账思想（设计原理 · 改编号/时间戳/锚点/凭证相关协议前必读）

> **分层原理**：文档协议**不做、也做不到实时监督** AI——监督是 tools\ 脚本层职责（检查点 1~7 皆为确定性函数）。文档层的任务是**事后可审计**：每条声明至少有两个以上独立记录互证，偷懒、伪造、出错必然在对账时暴露。协议不为"AI 一定守规矩"而设计，为"**不守规矩必留痕**"而设计。

> **反激励原则**：任何冲突裁决规则**不得给伪造留收益**。教训：旧版"跨分支以时间戳后写为准"等于"谁伪造时间戳谁赢"——裁判规则作弊有奖即是漏洞。现行设计：时间戳仅作辅证、裁决归 MAP [裁决者]、撞号重试留痕——伪造无收益。

**四类对账锚点：**

| 锚点 | 载体 | 暴露什么 |
|---|---|---|
| 时间锚 | reports 文件名日期 · INDEX 行日期 · 交接时间戳 | 倒序/时间倒退 → 可疑（辅证启发式，不作裁决） |
| ID 锚 | `TASK-ID` / `EVENT-ID` / `DESIGN-ID` 创建后不可变，事件重试生成新 ID | 缺失回链 / 重复事件 / 非法状态 → 审计检查 |
| 身份锚 | AI 标识 `{平台}-{AI名}-{短码}` | 冒名/混写 → 对照 INDEX 行与卡上承接 |
| 凭证锚 | 改动点 commit hash（git 可用时） | 谎称改动 → git show 对原始凭证 |

> **编号规则是对账接口，不是格式偏好**：改编号格式/递增规则/登记要求 = 改检查点 4 的全部逻辑依据与 [接力] 链续接方式（见 B.6）——必须先过 A.2 交叉影响检查，grep 全包列同步清单后才动手。
