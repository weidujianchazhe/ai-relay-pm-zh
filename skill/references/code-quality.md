# 代码质量门禁

> **定位**：技能包协议正文之一（`references/`）。**语言无关**——不含任何语言专属工具与配置；按栈落地见 `adapters/{python,java,javascript}.md`（附录，不属正文）。
> **数值**：一律以占位符 {{config:code_quality.<键>}} 标注，**正文不写死任何阈值**——同一数值出现在两处即为漂移起点。查值顺序见 MANIFEST §数值口径。
> **级别**：`[强制]` 违反即打回｜`[推荐]` 默认执行，偏离须在任务简报或提交说明中写明理由｜`[参考]` 视场景选用。
> **可机检性**：每条标注 `[强制]`/`[推荐]`/`[参考]`；**机检实现见 `scripts/code_metrics.py`**，未覆盖的条款按 change-control 的晋升池处理。
> **可单独使用**：把 `scripts/code_metrics.py` 与 `scripts/_common.py` 拷进项目即可做机检——
> **不需要工作区、MAP 与 config**（阈值有脚本内兜底，与 `config/defaults.yml` 逐键一致由 gen_views 第 6 节校验）。

---

## 0. 设计原则：保下限、不封上限 [强制·规范自检]

- **[强制]** 约束对象是 **AI 产出的代码**，双重定位：**保下限**——对能力较弱的执行者，规模与结构硬限制是护栏，防止产出「能跑但没人敢改」的代码；**不封上限**——对能力较强的执行者，机械限制会消耗其输出预算并拖慢交付。
- **[强制]** **约束对象的边界（读错会误判）**：受约束的是**项目业务代码**——交付物本身。
  **技能包自带的工作流 / 工具脚本不在门禁范围内**（scripts/ 下的门禁、归档、对账脚本是**工具**，不是交付物；
  它们的正确性由 selftest_gates.py 的变异自检保证，不由三档阈值保证）。
  **需要时仍可手工度量**：python scripts/code_metrics.py <脚本目录> --ws=<工作区根> 照常输出，
  但那些 [拦截线] 是**参考读数**，不构成"违反本规范"——**边界要说清楚，否则工具代码的读数会被当成项目的债**。
- **[强制]** 增删或收紧任何条款前先回答判据：**这条规则是在抬下限，还是在压上限？** 只抬下限、不压上限的规则才应收紧——这是阈值与条款增删的唯一裁量标准。
- **[推荐]** 规则的价值不在条文完备，而在「明确评审者在意什么」，减少来回返工。
- **[强制]** **阈值是团队基线，不是绝对裁判**：同一个数字在不同项目里的含义不同——
  这正是「数值只在**实例 MAP 规则段**与**出厂默认**各存一份」的原因，也是三档语义存在的理由。
  拿阈值当"质量标准"去否定一段人人看得懂的代码，是把**护栏**用成了**裁判**。

### 0.1 规范前置：从一开始就写对 [强制]

- **[强制]** **速查卡随任务下发**：任务简报附本包 `references/cheatsheet.md`（一屏），**不附细则全文**——守最小注入。
- **[强制]** **写明风格参照文件**：简报注明本项目的标杆文件；**风格是抄会的，不是读规范会的**（见 `references/code-style.md` §S5）。
- **[强制]** **写完即校**：每完成**一个文件**立即跑该栈的 lint 与格式化，禁止整批写完才校。
- **[强制]** **首件抽查**：任务产出的**第一个文件**完成即交复核——跑偏在 10% 进度纠正，成本是 100% 后返工的十分之一。

## 1. 规模阈值：三档口径 [强制]

- **[强制]** **三档语义**：**推荐线**＝理想目标、不强制，不落工具，交静态分析平台与人工评审提示；**预警区**＝允许存在、**但必须写明未拆分原因**，不阻断，理由由回查流程判定真伪（§2.3）；**拦截线**＝只卡明显失控的代码，流水线以非零退出码阻断合并。

| 指标 | 推荐线 | 预警区（须写原因） | 拦截线 |
| --- | --- | --- | --- |
| 函数长度 | `{{config:code_quality.func_lines.recommended}}` | 至 `{{config:code_quality.func_lines.warning}}` | > `{{config:code_quality.func_lines.blocked}}` |
| 嵌套深度 | `{{config:code_quality.nesting_depth.recommended}}` | 至 `{{config:code_quality.nesting_depth.warning}}` | > `{{config:code_quality.nesting_depth.blocked}}` |
| 圈复杂度 | `{{config:code_quality.cyclomatic_complexity.recommended}}` | 至 `{{config:code_quality.cyclomatic_complexity.warning}}` | > `{{config:code_quality.cyclomatic_complexity.blocked}}` |
| 文件长度 | `{{config:code_quality.file_lines.recommended}}` | 无（两档同值＝只有一条硬线） | > `{{config:code_quality.file_lines.blocked}}` |

- **[强制]** 上表是**全项目唯一**的规模口径。历史上并列存在过的单函数单一数值、Java 工具配置里另行硬编码的文件长度值等一律并入本表，**不得再有第二套数值**。
- **[推荐]** 预警区是整个设计的着力点：不一律适用，但留有「钩子」——超限必须落一笔可回查的案底（§2）。

### 1.1 行数口径（唯一）[强制]

- **[强制]** 上表所有「行」以**有效代码行**为准（口径键 `{{config:code_quality.file_lines.unit}}`）：去掉空行、纯注释与文档注释后的行数；函数长度与文件长度同一口径。**理由**：注释制度是 `[强制]` 而规模阈值是 `[推荐]`，若以物理行判定，**注释写得越规范越容易「违规」**——两者内在冲突，强制优先。
- **[推荐]** **物理行超限不必强拆**，但须在提交说明中同时写明物理行数与有效行数，供评审判断。
- **[推荐]** 已知豁免一经消化即**自动关闭**：豁免条目须写明触发条件与关闭条件（豁免条目达标后即失效）。

### 1.2 为什么工具只配拦截线 [强制]

- **[强制]** 所有落地检查工具**只配拦截线**，推荐线交静态分析平台与人工评审。理由一：工具配两套数值会互相矛盾（实测形态：工具与文档各写一个互不相同的数值）；理由二：用流水线阻断「未达推荐线」的代码，会把规范变成纯粹的官僚成本——那正是「压上限」。
- **[强制]** 阈值调整（§2.5）必须**同时**改配置与各栈工具参数；文档与工具数值漂移是规范失效的首要原因。

### 1.3 超限即信号：规范的第二重身份 [强制]

- **[强制]** 超限标注与豁免记录不是「备忘」，而是**设计债探针**：代码真写到超限，往往本身就是问题的暴露——问题通常不在「未拆分」，而在职责混杂或结构选择不当。
- **[强制]** 因此「写明原因」等于强制在代码里**留下案底**供回查（§2.3）。本门禁不只是质量检查器，还是**设计问题探测器**：规则拦截的是「写得太长的代码」，暴露的是「想得太乱的模块」。

### 1.4 门禁读数可信 [强制]

- **[强制]** **门禁必须上报自己的扫描范围**：文件数、作用域（哪些包/目录被检查）、排除项。「退出码 0」只有在扫描范围达标时才等于合格——否则只是**没看**。
  达标线＝扫描覆盖不低于 `{{config:code_quality.scope_min_percent}}`（机检实现见 `scripts/code_metrics.py` 的 `report_scope()`：覆盖不足直接报 `[问题]`，让"退出码 0"无法被冒充）。
- **[强制]** **扫描范围收窄必须显式声明**（如「某目录暂缓」），并写明**恢复条件**；禁止静默排除。
- **[强制]** **例外清单必须机器可读**：豁免/排除写在文档里而脚本读不到，会让已豁免项每次报红，逼每个接手者手工分诊「这条红是不是我的」。

## 2. 豁免机制 [强制]

### 2.1 标注要求

- **[强制]** 豁免必须**标注 + 必写原因**：豁免标注后必须紧跟实质原因文本，缺原因即形式违规，机器直接拦截；原因去空白后不得短于 `{{config:code_quality.exemption.min_reason_chars}}` 个字符。
- **[强制]** 例外是**场景分类而非许可证**：算法实现、协议解析、状态机、业务规则引擎等**逻辑高度耦合**的代码——强行拆分反而破坏可读性，拆出的子函数无法独立理解，则拆分无实益。
- **[强制]** 命名类豁免走**白名单登记表**（登记项 = 名字 + 豁免原因），不走行内标注。

### 2.2 敷衍词黑名单

- **[强制]** 原因文本命中黑名单即判不合格，清单由 `{{config:code_quality.exemption.hollow_words}}` 提供——**词表只有一处正本**（config），此处不复述副本。
- **[强制]** **判定技巧（把理由当变更描述来审）**：遮住代码只看注释——若该理由套在任何超长函数上都成立，它就是没有信息量的套话。

### 2.3 定期回查（豁免审计）

**操作清单（照做即可，别凭印象）**：

```
① 取清单     python scripts/code_metrics.py <源码根> --ws=<工作区根> --exemptions
             —— 全部豁免标注与预警区条目 + **聚集度**（同文件条目数降序），恒退出 0。
             **不要靠 grep 收集**：漏掉的恰恰是最不想被看见的那几条。
② 逐条三问   ① 这条理由说的是「结构问题」还是「规模问题」？（规模问题＝该拆）
             ② 遮住代码只看理由，换个人能不能复现同一个判断？（不能＝没有信息量）
             ③ 有没有更小的改法能消掉这条豁免？（有＝它本来就不该存在）
③ 三选一归类 见下表（真例外 / 设计债 / 敷衍）
④ 留痕       结论写入 REVIEWS 元数据通道（一行一条：条目 · 归类 · 处置 · 机器戳）；
             标「设计债」的排入重构回合
⑤ 反哺       可形式化的敷衍模式 → 固化为流水线正则（§2.4 单向阀）；
             范例缺口 → 补进范例库；黑名单漏网的套话 → 追加进黑名单
```

- **[强制]** **周期** `{{config:code_quality.exemption_audit_days}}`（约每季度一次，或每个大迭代收尾），单次以一次短会为度。
  **责任人**：各模块 owner 盘点自己名下条目，技术负责人裁定归类争议。**产出**：一张分类处置表 + **至少一条流程或阈值改进建议**（没有改进建议的复盘＝走过场）。
- **[强制]** **全量收集，一条不漏**：既有豁免标注，也含预警区函数写的「未拆分原因」注释——预警区标注与豁免标注同等对待。
- **[强制]** 逐条三选一归类：

| 归类 | 特征 | 处置 |
| --- | --- | --- |
| **真例外** | 逻辑高度耦合，拆分确实伤害可读性；理由能让人「不看代码就预判代码形态」 | 保留，登记后不再复查 |
| **设计债** | 理由真实但暴露结构问题：职责混杂、选错模式、一个函数干两件事 | 建条目，排入重构（`references/code-style.md` §S4） |
| **敷衍** | 复述函数名、声称性能考虑却无数据、理由可套用于任意函数 | 限期补真实原因或拆分，二者选一 |

- **[强制]** **聚集度分析（本流程最高价值的产出）**：单条豁免不重要，**分布**才暴露问题——同一文件累计豁免达到聚集阈值 → 大概率模块边界错了，走重构第三阶段而不是逐函数修补；同一敷衍句式反复出现 → 范例缺口，补进范例库（`references/code-style.md` §S5）并写明「为什么这种写法不该豁免」；黑名单没拦住的新套话 → 追加进黑名单。

### 2.4 单向阀原则

- **[强制]** **人审查出一次、机器从此永远拦截**：回查中发现的每一种**可形式化**的敷衍模式，都必须固化为流水线正则或 lint 规则，然后从回查的注意力清单里划掉。理由：人只负责发现**新的**作弊模式，已知的交机器——否则回查会退化成每季度重读同一堆套话。

### 2.5 反哺阈值（低频）[参考]

- **[参考]** 回查数据攒够后（周期取回查周期的整数倍）检视阈值本身：真例外集中紧贴拦截线上方且普遍合理 → 拦截线可能压到了好代码，考虑上移或为该类目单列口径；预警区原因绝大多数是敷衍 → 「写理由」的激励设计失效，回到 §0 判据重新对齐。
- **[强制]** 任何阈值调整必须**同时**改 `config/defaults.yml`、各栈工具参数、以及引用该阈值的正文占位说明。

## 3. 分层宽松度 [强制]

- **[强制]** 同一规范体系内，严格程度**按代码位置分级**，不作全库统一适用；分级决定的是「哪些条款适用」，不是「阈值可以放宽」：

| 代码位置 | 立场 | 具体体现 |
| --- | --- | --- |
| **原型 / POC** | 上限优先 | 「能跑就行」，允许适度违反设计原则 |
| **简单 CRUD** | 不折腾 | 直接数据访问，**禁止过度分层** |
| **核心业务逻辑** | 下限优先 | 严格遵循设计原则，严格捕获异常，覆盖率取核心业务线 |
| **安全模块**（认证/加密） | 最严 | 逐行审查，**禁止简单兜底** |

- **[强制]** 分层与「任务难度分级」是同一根轴的两个投影：难度高的任务必须配强执行者并强制复核（难度分级与强制复核）。

> **风格与工作方式（命名 / 版面 / 抽象 / 重构回合 / 范例库 / 提交信息）另见 `references/code-style.md`**——
> 它们靠人读与约定，无统一阈值，故不放在本文件。

## 4. 注释规范 [强制]

> 本节是**唯一**的注释条款——不存在第二套说法。

- **[强制]** **三层制**：模块与文件级说明（一句话职责 + 关键依赖）／公共类与函数级说明（用途、参数、返回、异常）／行内注释**写「为什么」不写「是什么」**。
- **[强制]** **密度是上限而非下限**：每个函数以函数头说明为标配，核心逻辑注释**按需**——有意图要解释时才写。区间见 `{{config:code_quality.comment_density.min_per_function}}` 至 `{{config:code_quality.comment_density.max_per_function}}`（该键的示例配置建议值见 §9）。理由：对自解释性好的代码，凑数的注释只能是**翻译式注释**，是噪音，会稀释真正有价值的「设计意图／边界条件／风险点」注释；对强执行者是纯成本。
- **[强制]** **禁止**：翻译式注释（「该函数用于 XXX」）、解释一眼能看懂的语法、**注释与代码逻辑不一致时保留注释**（失真比没有更毒——以代码为准，删注释）。
- **[强制]** **同步律**：改码必改注、删码必删注。
- **[强制]** **设计回写律**：实现若偏离冻结设计的已定参数、粒度或契约，须在提交流程（closeout）前提出**回写目标**（哪份设计文件哪一节）由主责方落账；**禁止只改注释不回写设计**——同步律只管「代码 ↔ 注释」，本条约住「实现 ↔ 冻结设计稿」，二者缺一即留分叉。
- **[强制]** **修缺陷必留痕**（现象 → 根因 → 修法，防后人当冗余删掉导致复发）；**约束与不变量显式声明**（调用顺序、线程约束、「为什么不能改」，防顺手优化）；**魔法数字禁止裸写**（常量提行、阈值写明来源）；**待办必须带归属**（「待办（任务号）：说明」，无归属待办由评审清退）。
- **[推荐]** **设计引用回链**（关键实现注明设计板编号或确认点，便于追溯）；**只增信息不增噪音**（以上之外不加仪式性注释——密度越高失真风险越大）。

## 5. 依赖方向与分层 [强制]

- **[强制]** **依赖单向、无环**：`api → services → repositories → models`；`common` 可被任何层引用，**禁止反向依赖与循环依赖**（分层名称由项目实例声明，分层方向由项目实例声明）。**禁止跨层引用**，如 `api` 层不得直接引用 `repositories` 层。
- **[强制]** **职责守恒**：新功能先查项目的模块归位表，归哪写哪；**禁止塞进「顺手方便」的旧文件**。
- **[强制]** **动工前先搜索**项目内是否已有可复用实现；**禁止新建与已有服务或类重复的实现**；不确定的设计意图写成 `[TODO: 待确认]`，**禁止编造**。
- **[强制]** **重构先声明**：搬函数、改接口须注明「范围 + 影响面」；**修缺陷的任务只修缺陷**，禁止夹带大重构。
- **[推荐]** **拆分触发即执行**：文件逼近 `{{config:code_quality.file_lines.recommended}}`，**或**一个类出现两套不相关的分节。可执行判定标准：按分节把方法分组后，**两组之间无共享实例状态**（不读写同一批字段）＝应拆；反之有共享状态则先内聚重构再议。
- **[推荐]** **膨胀审计**：比设计时大出明显量级的文件或函数重点审查，**膨胀必须能说出理由**。
- **[强制]** **依赖闭包与代码一致**：代码**实际引用**的第三方包必须与依赖清单（`requirements.txt` / `pyproject.toml` 等）登记的一致。**实际用到却未登记**＝交付即崩；**登记了却没人用**＝噪音。两者靠人眼维护则必然漂移——**这是门禁该抓的项**。

## 6. 异常、断言与错误自愈 [强制]

- **[强制]** **只捕获能恢复的异常，禁止吞异常**；禁止空捕获——空捕获的例外命名白名单（`expected` / `ignore`）见各栈适配器，**命名白名单是形式豁免，不等于可以静默**。
- **[强制]** **禁止用异常做流程控制**（其开销远高于条件判断）；预期内的正常分支（缓存未命中、文件不存在）与可预检查的错误应使用条件判断而非捕获；**禁止在 `finally` 中改变控制流**（返回、跳出）。
- **[强制]** 日志必须走日志框架，**禁止打印堆栈、禁止裸打印调试**。**豁免**：命令行入口面向终端的功能性输出（报告、表格、进度）不属「打印调试」——该类输出本就是产品面，改投日志会丢失标准输出的可管道性；豁免须以**显式路径登记**在门禁脚本中，库层与界面层**禁止借用**。
- **[强制]** **失败路径必须有归宿**：无静默吞异常，异常处理不得只记录不处理（ERROR 必对应处理路径）；**禁止密钥、隐私、凭据入日志**。
- **[强制]** **断言分载体**：关键路径函数入口用断言校验前置条件（出错炸在源头）；但断言在优化模式下会被**完全剥离**，因此**对外接口、数据层入口、权限与路径边界的前置校验不得只用断言**，须显式抛出异常；**断言只用于内部不变量**（开发者自证，剥离后不产生安全缺口）。
- **[强制]** **先测后优（自愈纪律）**：禁止无证据的性能优化——慢了先做性能剖析定位热点，**只在热点动手**；性能敏感路径的取舍以数据为准。

### 6.1 独立复核：只查机器看不见的部分 [强制]

风格、类型、格式由工具先过滤；**复核聚焦机器判不了的四类**：

| # | 检查项 | 强度 |
|---|---|---|
| 1 | **设计一致性**：与卡 / 任务简报逐要点对照 | 全卡必查 |
| 2 | **注释质量**：同步律（改码必改注）/ 修缺陷留痕 / 约束声明 / 锚点回链 | 全卡必查 |
| 3 | **结构**：职责守恒 / 依赖单向 / 拆分触发 / 重构声明 / 膨胀审计 | 全卡必查 |
| 4 | **边界完备**：失败路径有归宿、无静默吞异常、无凭据入日志 | 抽查 |

- **[强制]** **执行者与复核者必须是不同标识**——同一标识自审等于没有复核（见 `references/collaboration.md` §2）。
- **[推荐]** **批次收尾组合审查**：一批做完时查 ① 重复实现 ② 跨卡命名一致性 ③ 交互与样式一致性 ④ 依赖方向违例 ⑤ 风格漂移——防「每一笔都对、合起来不成样子」。

## 7. 测试与覆盖率 [强制]

- **[强制]** **分层覆盖率**（口径键见 `code_quality.coverage.*`）：

| 代码位置 | 要求 |
| --- | --- |
| 核心业务模块 | 不低于 `{{config:code_quality.coverage.core_business}}` |
| 工具类 / 公共方法 | 不低于 `{{config:code_quality.coverage.util}}` |
| 界面渲染层 | 以端到端（E2E）测试为主，不强制单元测试（`{{config:code_quality.coverage.ui}}` 为不设线） |

- **[强制]** **豁免场景**：简单取值与设值方法、仅做透传调用的第三方库适配层、纯数据访问方法。
- **[强制]** **阶段门槛不另立字段**：项目若需要低于终态线的阶段性门禁，在**实例配置**中覆写 `{{config:code_quality.coverage.core_business}}`，**不得新增第二个覆盖率字段**——两套数值是本规范明令禁止的形态。
- **[强制]** **每轮重构后必须运行测试验证**（流程见 `references/code-style.md` §S4）。
- **[推荐]** **手段分层**：单元测试与覆盖率报告是门禁基线；异常注入测试（模拟外部依赖超时、脏数据）用于核心管线。**测试是补充不是替代**——机器拦得住类型与风格，拦不住「实现偏离设计」。

## 8. 算法与性能纪律 [强制/推荐]

- **[强制]** **自研禁区**：密码学 / 哈希 / 压缩一律用成熟库，**永不手搓加解密**；搜索 / 排序 / 去重优先标准库与框架内建。
- **[强制]** **先测后优**：见 §8——无证据不优化。
- **[推荐]** **复杂度红线**：随数据增长的路径禁 `O(n²)`；千条量级必须可用。

## 9. 配置键清单（与 `config/defaults.yml` 的接口）

**接口清单**：正文只引用键名，**数值只在 `config/defaults.yml` 与实例 `MAP.md` 规则段各存一份**。

**每个键必须有一个「执行者」**——四类：**脚本**（本包机检）· **平台**（CI / 静态分析 / 覆盖率工具）· **人检**（判断类，不可能机检）· **未实现**（规范债务）。
**没有执行者的条款等于没有条款**，所以这张表同时也是**规范债务清单**——由 `scripts/gen_views.py` 第 7 节核对：正文引用了却没登记执行者的键会报红。

| 键 | 用途 | 本文出处 | 执行者 |
| --- | --- | --- | --- |
| `code_quality.func_lines.{recommended,warning,blocked}` | 函数行数三档 | §1 | **脚本**（拦截线 + 预警区） |
| `code_quality.nesting_depth.{recommended,warning,blocked}` | 嵌套深度三档 | §1 | **脚本** |
| `code_quality.cyclomatic_complexity.{recommended,warning,blocked}` | 圈复杂度三档 | §1 | **脚本** |
| `code_quality.file_lines.{unit,recommended,blocked}` | 单文件行数 + 行数口径 | §1.1 | **脚本**（只实现 `effective` 口径；实例声明其它口径会输出 `[建议]`） |
| `code_quality.comment_density.{min_per_function,max_per_function}` | 注释密度（**条/函数**） | §4 | **脚本**（只查上限；函数数 < 3 不判，防小文件噪声） |
| `code_quality.exemption.{min_reason_chars,hollow_words}` | 豁免闸门：理由长度 / 敷衍词黑名单 | §2.1 · §2.2 | **脚本** |
| `code_quality.scope_min_percent` | 门禁读数可信：扫描覆盖下限 | §1.4 | **脚本** |
| `code_quality.coverage.{core_business,util,ui}` | 分层覆盖率 | §7 | **平台**（coverage / JaCoCo 等；跑测试不在本脚本职责内） |
| `code_quality.exemption_audit_days` | 豁免回查周期 | §2.3 | **人检**（"理由真伪"是判断，不是计算） |
| `code_quality.reuse.extract_threshold` | 重复代码提取触发线 | `references/code-style.md` §S3 | **人检**（评审与重构回合的判断；"该不该提取"是语义判断，见下行说明） |

**为什么 `reuse.extract_threshold` 的执行者是「人检」而不是「未实现」**：
"两次重复该不该提取"取决于**结构相同还是语义相似**（`references/code-style.md` §S3 明写：结构完全相同 → 达线即提取；仅语义相似 → 并入重构回合观察）。
这是**语义判断**，机器无论怎么算都会误判——而本包的口径是「误报掩盖真实问题是门禁的首要失效原因」。
所以它的执行者是**评审**：数值是**评审时的锚点**（防止"看到重复就抽"的过早抽象），不是流水线阈值。
**判定标准**：把一条条款从「未实现」改判为「人检」，不是把债务藏起来，而是**说清它由谁执行**；真正的债务＝连执行者都指不出来的条款。

- **[强制]** **新增键的顺序**：先在 `config/defaults.yml` 定义，再在正文引用。**正文引用了未定义的键＝门禁无法解析**。
- **[强制]** **未知键必须显式报错，不得静默取默认值**：静默回退会让「没配」看起来像「配好了」，是**假账**的一种形态（见 `references/audit.md` §6）。
