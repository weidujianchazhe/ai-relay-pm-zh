# 设计（Design）

> **何时读**：一件事**要先定方案再动手**时（改结构、定接口、选技术路线、影响面大）。
> **不在接手路径上**：设计卡不是接手必读物——接手只读任务卡 + 指针指向的一篇记录。
> **但设计对话本身很贵**：本文件的重点就是**把这份成本压下来**（见 §2）。
> **可单独使用**：任意目录下 `designs/<卡名>.md` + `designs/<卡名>.blueprint.html` 两份文件即成立，
> **不需要工作区、索引、快照与任务卡**（两条命令：`new-card --design` 建、`design-archive` 收）。

---

## 0. 设计区是**规划层**（职责重定义 · 先读本节）[强制]

> **设计区不是「记录我想做什么」，而是把已经论证过的工程意图，形成足够完整、稳定、可追溯的【结构依据】，
> 使任务进入执行后【不需要重新发明设计】。**

**职责边界（三者不得互相侵占）**：

| 层 | 回答 | 不负责 |
|---|---|---|
| **设计区（本文件）** | **想清楚并留下依据**：为什么要做 · 做成什么 · 放在哪儿 · 边界在哪 | ❌ 不规定「分几张任务卡」 · ❌ 不做工程验收 |
| **任务区** | **按依据执行**：把已定稿的设计落成可执行工作单元 | ❌ 不在执行期重新解释 / 重新发明设计 |
| **全局工程审查** | **实际工程最终是否合格** | ❌ 不进设计区（验证是全局工作，不是设计步骤） |

### 0.1 三类设计资产**必须分开** [强制]

| 资产 | 位置 | 说明 |
|---|---|---|
| **当前有效设计** | `designs/`（根，扁平） | 工程**真正采用**的设计依据 |
| **设计过程资产** | `designs/`（根）或板块目录内 | 修改 / 迭代中的**中间方案、局部方案、论证材料** |
| **历史归档** | **`designs/archives/`** | 被替代 / 废弃 / 否决 / 过期的设计（**与任务归档 `archives/done/` 分离**） |

### 0.2 载体按「主要认知载体」选择（**不做类型硬绑定**）[强制]

> **原则**：设计资产采用**最适合表达其主要认知内容**的载体；**允许一个设计同时存在多个互补载体**。
> **不做**「功能类=HTML、技术类=MD」这类**按标签硬绑**的规则（真实设计经常跨界）。

| 设计内容 | 推荐载体 |
|---|---|
| UI · 页面 · 交互 · 状态变化 | **HTML**（人可直接打开看 / 验证） |
| 架构 · 技术路线 · 模块设计 · 数据结构与数据流 | **Markdown**（主），可配 HTML |
| 复杂结构关系 | **HTML / SVG**（可视化） |
| 综合设计 | **HTML + Markdown** 互补 |
| 局部 / 板块设计 | `designs/<模块>/design.md` + `designs/<模块>/blueprint.html` |

★ **新设计先执行，存量不强迁**（不做全仓库格式迁移）。

### 0.3 「可开工」的**本质门**（只问两句，不设页数）[强制]

**设计定稿 ≠ 实施准备完成。** 进入实施前，必须能**从设计 + 骨架回答**：

1. 这项工作在**项目整体结构中的位置**是什么？（新项目：**准备建立什么结构**；已有项目：**现在真实存在什么结构**）
2. 实施时**依据什么结构**进行？（落点 / 影响面 / 顺序与依赖 / 可独立与不可独立）

> **答得出 → 开工**（用半页还是三页**不由规则决定**——保下限、不封上限）；**答不出 → 不开工**（或**退回设计**）。
> **本门不要求「必须有 N 张任务卡」**：任务卡是**可选**的执行载体；核心门禁是「**是否已完成工程级实施分析**」。

### 0.4 设计骨架 = **项目当前工程模型** [强制]

`designs/SKELETON.html`（人读 / 可视化）· `designs/SKELETON.md`（AI 读 / 文字依据）——
★★ **两者是【同一份「项目当前工程模型」】的两种阅读方式，不是两个权威源**（防「AI 看到 A、人看到 B」的新漂移）。

**它是一等工程对象** ✓：新 AI 第一次接手时，回答「**这个项目现在是什么结构**」的**唯一可信入口**（不必自己拼多处）。

**与相邻载体的分工（不得互相侵占）**：

| 载体 | 回答 |
|---|---|
| `MAP.md` | **环境与规则**：项目在哪 · 代码在哪 · 按什么规则运转 |
| `STATE.md` | **当前运行状态**：快照 |
| **`SKELETON`** | **当前工程模型**：项目由什么组成 · 模块与依赖 · 设计落在哪 |

骨架**至少**包含（**不是索引** ✗）：**① 总体架构 ② 模块关系 ③ 数据 / 调用主路径 ④ 工程板块·模块·路径 ↔ 当前有效 `DESIGN-ID`（结构↔设计双向可追溯） ⑤ 当前设计边界**。

> **双向可追溯（P1）** ✓：**不给代码文件绑 `DESIGN-ID`** ✗（会膨胀）——关系建在**结构层**：`工程板块/模块/路径 ↔ SKELETON ↔ DESIGN-ID` ✓。
> **设计变更传播（P0）** ✓：设计变更（v1→v2 / 废弃）时，必须登记「**受影响结构**」与「**受影响任务**」，并写 `EVENT-ID` ✓——**不得只改一个 Markdown** ✗。
> **任务完成 ≠ 设计失效（P0）** ✓：任务全部完成**不**使设计失效——设计可能仍是**当前工程基线**，继续作为对照依据 ✓。
> **暂不实施 / 基线保留（P0）** ✓：设计可「**有效但不立即实施**」（未来规划 / 架构基线 / 设计库存）✓——它是**合法状态**，不是「待办」✓。

## 1. 一份设计＝两份文件（形态契约）

| 文件 | 名字 | 收什么 | 谁看 | 变化节奏 |
|---|---|---|---|---|
| **详述** | `designs/<卡名>.md` | **叙述**：范围 / 非目标 / 不变式 / 迁移与回滚 / 验证证据 / 决策理由 | AI 执行时对照 | **定点改**：只动受影响的行 |
| **蓝图** | `designs/<卡名>.blueprint.html` | **结构**：模块与依赖图 / 文件清单 / 数据与调用流 / 改动点 / 里程碑 | **人看**（确认方向） | **整篇重写**：一轮一版 |
| **骨架** | `designs/SKELETON.html` + `designs/SKELETON.md` | **项目当前工程模型**：总体架构 / 模块关系 / 数据与调用主路径 / **工程板块·模块·路径 ↔ 当前有效 `DESIGN-ID`** / 当前设计边界 | 人（HTML）+ AI（MD） | 设计增删/替代时刷新 |

**为什么必须分开**：两类内容的变化节奏不同——
**叙述**是累积的档案（一次写对，之后只补几行）；**结构**是每轮都要重看的当前共识（方向一变全变）。
挤在一个文件里，结果是**每轮修订都得重发那份长叙述**——这正是设计对话最大的成本项。

> **判定一段话该放哪一份的一句话**：**能画出来的放蓝图，只能讲清楚的放详述。**
> 蓝图里出现长段落＝放错了位置；详述里出现框图和清单＝重复维护（迟早漂移）。

## 2. 成本纪律：一轮设计对话该产出什么

**先诊断**：贵不在"写长文"，在**每轮修订都重新输出全文**。
长上下文里的每一次更正，模型都要把设计重讲一遍——**方向未定时的长文，方向一变全部作废**。

**三条纪律**：

1. **先蓝图、后详述**。方向没定之前**不写详述**——蓝图短、改得快、给人看得懂；
   用户确认方向后再补详述。**先写长文再改方向，是本流程最贵的一种做法。**
2. **蓝图整篇重写，详述只吃增量**。每轮固定输出物是蓝图（一屏，重写代价低）；
   详述只做**定点修改**（改哪几行、改成什么），**禁止整篇重发**。
3. **改动留一行"为什么"**。定点改详述时，在被改段落后追加一行 `> 修订：<理由>（<机器戳>）`——
   不写理由的改动，等于把下一次对话重新拖回"从头讲一遍"。

**蓝图格式约束（受控格式，机器可查）**：

| 约束 | 上限 | 为什么 |
|---|---|---|
| 总行数 | `{{config:capacity.blueprint_max_lines}}` | **超线仅提醒，不阻断**；若已影响直观，把叙述移回详述 |
| 单个段落字符数 | `{{config:capacity.blueprint_max_para_chars}}` | 长段落＝把详述搬过来了，两份文件立刻开始漂移 |
| 允许的构件 | 小标题 / 表格 / 清单 / 代码块（框图） | 都是**一眼可扫**的结构；散文不是 |

> 检查由 `scripts/validate_workspace.py` 做（见 §6 契约表），**不靠人记得**。

## 3. 生命周期与定稿门禁

```
草案 → 评审中 → 已定稿 → { 实施中 / 已实施 / **暂不实施·基线保留** } ／ 已拒绝 ／ 已废弃
```

### 设计可以「先跳过」（显式决定，不是漏掉）

> 任何形态**都可以选择先跳过设计**（轻量、单任务卡都适用）——但**必须显式记在字段里**：
> 任务卡的 `DESIGN-ID` 填 **`先跳过`**（不是留空、也不是「—」）。这样「没做设计」是**有意识的决定**，而不是漏网；
> 日后要补设计：建好设计卡后，把该字段改成真实 `DESIGN-…` 即可（**单向、可追溯**）。
>
> **流程顺序（不许颠倒）**：先定两个位置 → **建项目目录 + 建管理区**（并 validate）→ **然后**才进设计环节（设计卡流程**全部保留**：蓝图 → 详述 → 定稿 → 拆任务卡）；
> 只有在设计环节选「**先跳过**」时才进入**建卡环节**（直接建任务卡，卡上 `DESIGN-ID` 记 `先跳过`）——**后续可再补设计**。
>
> **卡上引用设计卡时，`DESIGN-ID` 的值形如 `DSN-YYYYMMDD-XXXXXX`**（**`DSN-` 前缀**，不是 `DESIGN-`）——由 `closeout.py new-card --design` 生成，创建后不可变。
>
> **本体与附带**：**设计卡是本体**——拆分 / 归档 / 定稿门禁都以**卡**为准；**蓝图（网页视图）只是附带产物**，给人看「设计出来的东西长什么样」。
>
> **三种形态（卡片 / 轻量 / 完整）共用同一套模板与同一套流程**：形态只决定「用不用某个能力」，不改变文件结构与字段。

- **定稿门禁**：**只有「已定稿」的设计卡才能生成任务卡**；任务卡上必须回填 `DESIGN-ID`。
- 定稿 / 拒绝 / 废弃均写事件标识（启用稳定 ID 时）。
- **拆卡**：一张设计卡可拆成多张任务卡；拆出的每张卡 ID **登记回设计卡的「拆分出的任务卡」字段**——
  这个字段是归档门禁的判据（见 §4），**不是备注**。

**能力开关**：`collaboration.design_cards_enabled`（示例默认关）控制的是**门禁强制力**——
关着时设计卡可以当"方案笔记"用（不校验状态机）；打开时按本文件全量校验。
**无论开关如何，一份设计就是两件套**——这是形态契约，不是能力开关。

## 4. 设计区与设计归档（不放工作记录归档）

```
designs/                              ← 活跃设计（只放还没走完生命周期的）
    SKELETON.html / SKELETON.md       ← **设计骨架**（同一份骨架的两种阅读方式；设计区顶层入口）
    <主题>.md                         ← 详述（AI 执行时对照；定点改）
    <主题>.blueprint.html             ← 蓝图（**人看**；整篇重写）——**新设计用 HTML**；存量 `.blueprint.md` 不强制迁移
    <模块>/                           ← **板块独立设计**（可选）：该板块自己的 design.md + blueprint.html
    designs/archives/                 ← **设计归档**（用完/作废的设计两件一起移到这里；**与任务归档 `archives/done/` 分离**）
         <主题>.md
         <主题>.blueprint.html
```

> **归档路径口径（唯一）** ✓：**`designs/archives/`**（设计归档**在 `designs/` 之内**）——与 `archives/done/`（任务/工作记录归档）**语义与位置都不同**，不得混放。
> **载体契约（唯一）** ✓：蓝图 = **`<主题>.blueprint.html`** ✓（人读视图 ✓）；详述 = **`<主题>.md`** ✓（AI 对照 ✓）。**不得长期并存 `.blueprint.md` 与 `.blueprint.html`**（防双格式历史包袱）；存量按「**新设计先执行、不强迁**」处理。

**归档触发条件（满足其中一个即可）**：

| 条件 | 机器判据 |
|---|---|
| ① **设计已拆分成全部任务** | 状态＝已定稿 **且**「拆分出的任务卡」非「—」**且**其中每个 `TASK-...` 都能在 `tasks/` 或 `archives/done/` 里找到 |
| ② **设计作废** | 状态 ∈ {已废弃, 已拒绝} |
| ③ **暂不实施（不触发归档）** | 状态＝**暂不实施·基线保留** → **不归档、也不必拆任务**：它仍是对照基线 |

**为什么归档留在设计区，而不是工作记录归档区（`archives/done/`）**：

- `archives/done/` 的语义是「**这件事做完了**」——它是接手的证据链，接手者会按需翻。
- 设计卡走完流程后**对后续接手没有价值**：接手要的是"这张卡怎么干"，不是"当初为什么这么定"。
  塞进工作记录归档区，只会**抬高接手时的检索噪声**，换不来任何接手收益。
- **但它对复盘有价值**——所以只**移区、不删除**：落在 `designs/archives/` 里，属**留痕**（定点查，不整读，见 `references/artifacts.md` §8）。

**归档动作是机械步骤，交给脚本**：

```
python scripts/closeout.py <管理区> design-archive "<设计卡名>"
```

脚本负责：校验触发条件 → 详述与蓝图**两份一起移**（只移一份＝设计缺一半）→ 拒绝覆盖已有归档同名文件。
**设计卡不进 `INDEX.md`**（它不是交接记录），因此归档也不动索引与快照——
设计区的进出**不产生任何索引维护成本**。

## 5. 与任务卡、记录的关系

| 关系 | 约定 |
|---|---|
| 设计 → 任务 | 未定稿不生成任务卡；任务卡回填 `DESIGN-ID` |
| 任务 → 设计 | 执行中发现**设计偏离**：写进任务卡的「设计偏离」字段（冻结决策出处 + 理由 + 回写目标），不许静默改设计 |
| 设计 → 记录 | 交接记录的「数据影响」块须声明本轮核查过的设计文档；**没查**与**查了没有**必须分开写 |
| 设计 → 归档 | 拆分完毕或作废即归档（§4）；归档后不再回写 |

## 6. 契约表（本文件对实现的约定）

| 契约 | 冻结值 | 谁在消费 |
|---|---|---|
| 详述文件名 | `designs/<卡名>.md` | 设计区校验 / 归档脚本 |
| 蓝图文件名后缀 | `.blueprint.md` | 成对性校验 / 归档脚本 |
| 归档目录名 | `designs/archives/` | 归档脚本 / 路径注册表 |
| 设计卡状态 | 草案 / 评审中 / 已定稿 / **暂不实施·基线保留** / 已拒绝 / 已废弃 | 定稿门禁校验（启用时）；**「暂不实施」是合法态**（有效但暂不产生任务）|
| 归档门禁字段 | 「拆分出的任务卡」 | 归档脚本 |
| 蓝图长度（**超限仅提醒**）· 段落（**超限阻断**） | `capacity.blueprint_max_lines` · `capacity.blueprint_max_para_chars` | 结构校验脚本 |

> **改以上任何一项**＝改脚本接口：先过 `references/change-control.md` §A 第 2 条（交叉影响检查），grep 全包列出同步清单。
