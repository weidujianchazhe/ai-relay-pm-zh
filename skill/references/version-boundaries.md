## 10. 产品线分化：A 轻量应用版 / B 完整工程版

| 项 | **A 线：轻量应用版** | **B 线：完整工程版（本包）** |
|---|---|---|
| 产品名 | `ai-relay-pm-lite`（**独立版本号**，自 v2.6 起） | `ai-relay-pm-global`（沿用 v3.x） |
| 面向 | 普通人做网站 / 工具 / 自动化 / 小应用 | 复杂软件工程、底层系统、并发、资源安全、长期维护 |
| 技术面 | HTML / CSS / JavaScript / TypeScript / **Python**（Node 等按需） | Python / C / C++（后续按**准入判据**评估 Go / Rust 等） |
| 默认体验 | 简化初始化、简单任务清单、基础检查 | 完整管理区、任务卡与状态流转、分层质量门禁、审计证据链 |
| 刻意不做 | **不加入 C / C++**（不是删功能，是**面向不同门槛**） | **不为「市场覆盖」而加语言** |

**三条底线（两条产品线都不得删）**：

1. **变更必须有记录** —— 不得让 AI 改完却无法追溯；
2. **测试失败必须真实失败** —— 不得把「未执行」说成「通过」；
3. **AI 不得擅自替用户决定重要项目方向**。

**两条线的边界**：**共享经过验证的通用规范 / 模板 / 原则**（避免同一个 Bug 在两个包里各修一遍），
但**入口、默认流程、适配器各自独立**；**Lite 不依赖 Full 才能运行**；共享层只放**已在真实项目验证过**的规则。

**版本号约定**：A / B **各自独立编号** —— 不要让人误以为 Lite 升到某版本就能获得 Full 的能力。

**为什么这样分**：普通人做网站不该被迫先理解内存管理、并发模型与复杂工程审计；
反过来，做底层软件的人也不该因为「轻量化」而失去必要的工程约束。**两者不矛盾，但不能混成一个包。**

## 11. 版本号与产物刷新约定（**不为小改升版本**）

| 阶段 | 版本号 | artifact | 说明 |
|---|---|---|---|
| **开发期（累积中）** | **不变**（如 `3.9.0`） | **原地刷新**（同一文件名，覆盖） | 小改、澄清、缺陷修复**一律不升版本号**；**保持一个版本一个 artifact** |
| **定版（包主宣布）** | 固定 | **不可变** | 之后要改：要么修 P0/P1（须写 §8 开版原因），要么**升版本** |

**为什么这样定**：升版本号本身是一种**对外承诺**（"这是一个新版本"）。
为一次文档澄清或一行修正就升号，会让版本号**失去信息量**，也会制造"同内容多版本"的噪声。

**两条底线仍然成立**：

1. **同一版本号不得对应两个不同 artifact** —— 开发期用**覆盖刷新**（不是并存），定版后**不可变**；
2. **每次实质变更仍要在 §8 留下记录**（性质 / 原因 / 是否动 Core / 是否动阈值）—— 记录与版本号**解耦**。

**实践（本包已发生）**：`3.6.1` / `3.7.0` / `3.8.0` 曾因文档改动而升号 —— 属于**过度升版**；
自本约定起，同类改动**留在当前版本号内**（如 `3.9.0`），只在**里程碑或包主宣布**时才升号。
