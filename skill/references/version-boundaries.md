## 10. 产品线分化：A 轻量应用版 / B 完整工程版

| 项 | **A 线：轻量应用版** | **B 线：完整工程版（本包）** |
|---|---|---|
| 产品名 | `ai-relay-pm-lite`（**独立版本号**，自 v2.6 起） | `ai-relay-pm-global`（沿用 v3.x） |
| 面向 | 普通人做网站 / 工具 / 自动化 / 小应用 | 复杂软件工程、底层系统、并发、资源安全、长期维护 |
| 技术面 | HTML / CSS / JavaScript / TypeScript / **Python**（Node 等按需） | Python / C / C++（后续按**准入判据**评估 Go / Rust 等） |
| 默认体验 | 简化初始化、简单任务清单、基础检查 | 完整管理区、任务卡与状态流转、分层质量门禁、审计证据链 |
| 刻意不做 | **不加入 C / C++**（不是删功能，是**面向不同门槛**） | **不为「市场覆盖」而加语言** |

**三条底线（两条产品线都不得删）**：

1. **变更必须有记录** —— 不得让 AI 改完却无法追溯；
2. **测试失败必须真实失败** —— 不得把「未执行」说成「通过」；
3. **AI 不得擅自替用户决定重要项目方向**。

**两条线的边界**：**共享经过验证的通用规范 / 模板 / 原则**（避免同一个 Bug 在两个包里各修一遍），
但**入口、默认流程、适配器各自独立**；**Lite 不依赖 Full 才能运行**；共享层只放**已在真实项目验证过**的规则。

**版本号约定**：A / B **各自独立编号** —— 不要让人误以为 Lite 升到某版本就能获得 Full 的能力。

**为什么这样分**：普通人做网站不该被迫先理解内存管理、并发模型与复杂工程审计；
反过来，做底层软件的人也不该因为「轻量化」而失去必要的工程约束。**两者不矛盾，但不能混成一个包。**

## 11. 版本号与产物刷新约定（**不为小改升版本**）

| 阶段 | 版本号 | artifact | 说明 |
|---|---|---|---|
| **开发期（累积中）** | **不变**（如 `3.9.0`） | **原地刷新**（同一文件名，覆盖） | 小改、澄清、缺陷修复**一律不升版本号**；**保持一个版本一个 artifact** |
| **定版（包主宣布）** | 固定 | **不可变** | 之后要改：要么修 P0/P1（须写 §8 开版原因），要么**升版本** |

**为什么这样定**：升版本号本身是一种**对外承诺**（"这是一个新版本"）。
为一次文档澄清或一行修正就升号，会让版本号**失去信息量**，也会制造"同内容多版本"的噪声。

**两条底线仍然成立**：

1. **同一版本号不得对应两个不同 artifact** —— 开发期用**覆盖刷新**（不是并存），定版后**不可变**；
2. **每次实质变更仍要在 §8 留下记录**（性质 / 原因 / 是否动 Core / 是否动阈值）—— 记录与版本号**解耦**。

**实践（本包已发生）**：`3.6.1` / `3.7.0` / `3.8.0` 曾因文档改动而升号 —— 属于**过度升版**；
自本约定起，同类改动**留在当前版本号内**（如 `3.9.0`），只在**里程碑或包主宣布**时才升号。

### 8.12 v4.1.1 缺陷修复版（记录在案）

**为什么升号**：4.1.0 **已定版并发布**（tag / Release / ZIP），按 §11 底线 1「同一版本号不得对应两个不同
artifact」，定版后不可原地刷新；本次是 §11 允许的另一条路——**修 P0/P1 并写开版原因**。

**缺陷全部由外部实跑暴露**（非自查发现），符合 `MANIFEST` 的准入判据。

**P0-1 · `index-add` 对任何合法短号崩溃（exit 3）**

- **根因**：8.11 的 A 项把短号正则搬进配置时**丢了捕获组**——
  `ID_RE = ^([A-Z]{2})([0-9]{4,5})$`（两组）被改为 `_id_re = ^( + pattern + )$`（**一组**），
  而 `closeout.py:175` 仍按两组解包 → `ValueError: not enough values to unpack (expected 2, got 1)`。
- **影响**：整条提交链断在「登索引」一步；`crash_matrix` C4/C5 连带报红（夹具走的同一端点）。
- **修法**：新增 `_common.branch_split(whole, root)` —— 前缀 = **开头连续字母段**，序号 = 其余。
  **不写死 `[:2]`**（那是「第二个真值」，配置一改即漂移），故 `[A-Z]{3}[0-9]{4}` 时前缀自然变 3 位；
  **不做 pattern 内省**，格式合法性由调用方 `_id_re`（即配置 pattern）先行过滤。

**P0-2 · 同分支递增校验静默失效（同一根因的第二面，修 P0-1 时引入）**

- **根因**：`_id_re` 改为单组后，`closeout.py` 有**两处**消费它；首轮只修了 `:175`，
  漏了递增循环内的 `if m and m.group(1) == branch:` —— `group(1)` 是**完整短号**（`EN0050`）
  而 `branch` 是**前缀**（`EN`），**恒假** → 循环体永不执行 → `mx` 恒 0 → 判据空转。
- **为什么比崩溃更难发现**：`m.group(2)` 的 `IndexError` 被恒假条件挡住，**不崩、不报错、退出码 0**；
  实测索引已有 `EN0050` 时登记 `EN0001` → 被接受并插到 `EN0050` 之前（4.0.0 正确拒绝，exit 1）。
  **崩溃会自己暴露，静默失效不会。**
- **事后检测仍在**：`check_index` 对回跳报 `[问题] 同分支未递增`，故属**单层失效**，非数据静默损坏。
- **修法**：两处消费点统一走 `branch_split`，并加 `isdigit()` 保护（`_sort_key` 与递增循环）。

**P1 · 自检的正控覆盖不足（这是上述两个缺陷都逃过 19/19 全绿的原因）**

- `selftest_gates.py` **本来就有基线正控**（L25 明文 + `main()` 实跑「基线非 0 → 用例无效」），
  但**基线只覆盖各用例自己的夹具**，而夹具**手写 INDEX/冷区、从不调用 `index-add`**
  → **正控存在但覆盖不足**，不是「没有正控」。
- **补双正控**：
  - **正控 1（端点能不能跑）**：干净工作区 `index-add` → **必须 exit 0**；
  - **正控 2（判据还灵不灵）**：夹具预置 `EN0050` → 登记更小的 `EN0001` → **必须被拒（非 0）**。
- **负控实测（证明两面不冗余）**：把 L183 改回恒假 →
  **正控 1 仍通过 ✗**（端点确实能跑）· **正控 2 失败 ✓**（`判据空转：EN0001 被接受了`）· `18/19` · exit 1。
- **验证器分工（本版最重要的结论）**：`crash_matrix` 只验「写入有没有把数据弄坏」，
  **验不了「判据有没有在判」**——同一注入下它 `5/5` 通过、exit 0。
  端点崩溃 → `crash_matrix` + 正控 1 能抓；**判据空转 → 只有正控 2 能抓**。两类故障域不重叠。

**P2 · 申报与文档如实性**

- `config/defaults.yml` **去掉 UTF-8 BOM**（12,160 → 12,157 字节，**内容零变化**）——
  首轮申报「三处同步」而实际动了 4 个文件，本版补齐申报（符合 `scripts/README.md`「工作区文本一律 UTF-8（无 BOM）」）。

**设计原则（本节判据的检验对象）**：

> ★ **压缩掉的必须是【可重建路径】，不能是【不可重建的裁决依据】。** ★ **内容与「为何如此排序」要分开判** —— 前者可由「留痕见」指针重建，后者若无允许读取的正本即不可重建。
