# 语言适配层（Language Adapters）

> **一句话**：**规范与管理模型语言无关；语言只决定「取数探针」**。核心流程不允许出现语言分支。

## 1. P0 缝（已实现）

```text
COLLECTORS = {}                       # lang -> 取数探针
def collector(lang)                   # 注册装饰器
def analyse(path, lines, th, lang)    # 分派；未注册 -> None
```

**探针契约**：输入 `path / lines / th`，返回 `[(kind, lineno, msg)]`，kind 三值：

| kind | 含义 | 处置 |
|---|---|---|
| `block` | 拦截线（超线即阻断） | 计入问题，退出码 1 |
| `warn` | 预警区（须写明原因） | 走豁免机制；未说明 -> 问题 |
| `tbd` | **待核**：语言已识别但**未接线** | 报待核；**不猜度量、也不静默通过** |

**未注册语言的行为**：`analyse()` 返回 `None` -> 调用方报「本轮不做度量」；若**只点名了非已适配语言** -> **待核 + 指路**（不许静默通过）。

### 1.1 语言相关注册表关系（**四个注册表，各答一问；不合并**）

| 注册表 | 位置 | 回答的问题 | 性质 |
|---|---|---|---|
| `ADAPTERS` | `scripts/eng.py` | **这个语言的落点是什么**（能力动词路由） | 意图上的**唯一语言落点** |
| `COLLECTORS` / `PENDING` | `scripts/code_metrics.py` | **怎么取得某类度量**（取数探针） | 度量注册表 |
| `CODE_CHECKERS` / `PENDING_LANGS` | `scripts/known_defects.py` | **怎么检测某类缺陷**（缺陷召回） | 缺陷注册表 |
| `providers` | `config/providers.json` | **外部 Provider 能提供什么能力** | Provider-backed **档案正本** |

> **为什么不合并**：四者回答的是**不同问题**，合并会制造伪统一。**Core 原生能力（如 Python 的度量/检查器）不经 Provider 档案** —— 故 `providers.json` 不含 `python` 是**设计**，不是缺口。
> **四者的共同真值**：语言是否**已适配** —— 以 `ADAPTERS` + `COLLECTORS` + `CODE_CHECKERS` 的**实际接线**为准（`providers.json` 只覆盖 Provider-backed 部分）。

## 2. 能力接口（Capability Verbs）

> 核心流程**只说动词，不说工具**；工具由适配层决定。

| 动词 | 含义 | Python | C / C++ |
|---|---|---|---|
| `INSPECT` | 取数（度量） | `ast`（本包已实现） | `clang-tidy` / `cppcheck` / `lizard` |
| `BUILD` | 构建 | `pip install -e .` | `cmake --build build` |
| `TEST` | 测试 | `pytest` | `ctest` / `gtest` |
| `AUDIT` | 审计（编排门禁） | `audit_all.py`（**已实现**：`eng.py AUDIT` 路由到编排器，**不判语言**） | 同上（语言无关） |
| `VERIFY` | 验证（构建 + 测试 + 审计都过） | 同左 | 同左 |

## 4. 接线一个新栈（标准动作）

1. 在 `scripts/code_metrics.py` 注册 `@collector("<lang>")`；
2. 探针**调用该栈成熟工具**取数，**绝不自己写解析器**（禁止让本技能变成第二套编译器）；
3. 工具未就绪时：**返回 `tbd` + 指路**，**不许返回空列表**（空 = 恒绿门禁）；
4. 在 `adapters/<栈>.md` 写下：工具、命令、输出解析、失败样例；
5. 用 `scripts/lang_gates.py record` 留痕。

## 5. 本层不做什么

- **不**在核心流程里加语言分支（只在 `COLLECTORS` 注册）；
- **不**自己实现 C/C++ 解析器、编译器、构建系统；
- **不**把「未测」写成「通过」；
- **不**让阈值口径分叉：**三档阈值默认全语言共用**（从实例 MAP 读）；**按语言/项目覆盖是允许的，但必须由证据触发**（见 §6 与 §13）。
## 6. 「取数探针」声明格式与输出契约（v3.x）

**MAP 规则段声明**（每条 `<lang>=<命令>`，多条用逗号分隔；**核心不写死工具名**）：

```text
- **取数探针**：`cpp=<provider 命令>`，`c=<provider 命令>`
  —— **provider 必须逐行输出 JSON**（§6 的输出契约）。工具原生输出（cppcheck `--xml`、clang-tidy YAML、lizard 文本）**不能直接当 provider**，
  **必须先经一个薄适配器转成 JSON**（见下方「Provider 适配器」）。
```

**输出契约**：探针向 stdout 逐行输出 JSON，键：

| 键 | 含义 | 必填 |
|---|---|---|
| `func` | 函数/过程名 | 是 |
| `eff_lines` | 有效行数 | 是 |
| `ccn` | 圈复杂度 | 是 |
| `nest` | 嵌套深度 | 是 |
| `file` | 文件（可选，仅用于展示） | 否 |

**判分默认走同一套三档阈值**（从实例 MAP 读）：探针只负责**取数**，`judge` 逻辑**全语言共用**；
**参数可按语言覆盖，但覆盖必须有证据**（先建「语言差异表」→ 用真实项目数据证明该语言确实需要不同阈值 → 才落成配置）。

**工具不存在 / 未声明 / 解析失败** -> `[待核]` + 指路（**绝不伪装成功，也绝不用桩数据冒充真数据**）。

## 7. 核心原则：注册了 ≠ 生效了（本包实测得出）

一个能力必须走完整条阶梯，才算**真的存在**：

```text
Declared -> Registered -> Discoverable -> Invocable -> Executed -> Observed -> Verified
 声明   ->   注册     ->   可发现     ->  可调用   ->  已执行  ->  有结果  ->  已验证
```

**本包的真实案例（v3.0.0 开发中实测）**：C/C++ 探针**已声明、已注册、可发现**，
但**永远不被调用**（`main()` 早期 `return` 短路）—— 只看代码会以为"做完了"，**实测跑一次才暴露**。
修完后又暴露第二处：钩子内 `run()` 被同名变量遮蔽 -> `TypeError`，即**可调用但调用失败**。

**因此本包的规矩**：

1. **声明不是证据**（`MAP` 写了 `languages=[cpp]` ≠ 有 C++ 能力）；
2. **注册不是生效**（`@collector("cpp")` ≠ 会被调用）；
3. **桩验证只证明"扩展机制可用"**，**绝不算作该语言接线完成**；
4. 每个新栈的验收必须走到 **Executed + Observed + Verified**（本机或 CI 上真跑出结果）。
## 8. Environment Preflight（环境前置确认 · **不安装、不携带**）

> **默认语言 = Python。** 只有项目声明了**非默认技术栈**（Native C/C++ 等）时才触发本确认。
> **本技能不安装工具链、也不携带工具链**；它只负责**识别需要什么、检查有没有、没有就明说**。

**触发时机**：新建项目选择技术栈时 / 首次进入一个非默认栈的工程时（**只在第一次**，之后按 Project Profile 执行，不重复追问）。

```text
项目技术栈（步 0.5 的选择）
   ├── Python（默认）            -> 无额外环境要求，直接创建
   └── Python + Native C/C++     -> Environment Preflight：
          需要什么？（从 MAP 的 Project Profile 读：语言 / 构建系统 / 测试 / 工具链 / 取数探针）
          有没有？（只检查，不安装）
              有 -> 继续创建 / 继续执行
              无 -> **先告诉用户缺什么、要他自行安装**；依赖该能力的操作 -> [待核]
```

**提示语模板（照读）**：

```text
检测到本项目包含 C/C++。开始前请确认开发环境已就绪：
  · C/C++ 编译器（GCC / Clang / MSVC 任一）
  · 项目声明的构建工具（如 CMake）
  · 项目实际使用的测试工具
  · （可选）静态分析器（cppcheck / clang-tidy）
本技能**不会自动安装**这些工具，也不随包携带。
环境已就绪 -> 继续；尚未就绪 -> 请先完成安装（装好后我会复用你环境里的工具）。
```

## 9. 工具链原则（**契约级，不得违反**）

1. 技能包**不携带** C/C++ 编译器、构建系统或静态分析器；
2. 技能包**不因执行能力而自动安装**第三方工具；
3. 能力执行**优先复用**目标工程 / 用户环境**已有**的工具；
4. 工具**不存在**时，结果必须是 **TBD / 待核**，**不得是 PASS**；
5. 工具**存在**时，必须**真实执行并透传结果**（不得空转）；
6. 能力矩阵**不得通过安装工具**来人为制造绿色结果；
7. **Project Profile 是"声明"**：声明需要什么，不等于环境已经具备——执行时仍要**实测环境**。

**为什么写死这七条**：本技能 < 1 MB，只依赖 Python 标准库；一旦因为"想让矩阵变绿"而引入工具链安装，
一个工程管理技能就会**变成开发环境安装器**——那是方向的崩塌，不是功能的增强。

## 11. 语言层级原则（Python ↔ C/C++ 的关系）

> 本 Skill 里 Python 与 C/C++ **不是两个平行的「语言支持项」**，而是**两个不同抽象层级的工程观察工具**。
> 引入 C/C++ **不是为了多一种语言**，而是**为了防止把高层抽象误认为系统真实状态**。

**默认与例外**：

- **Python 是默认的高层实现工具**（业务逻辑 / 自动化 / 工具 / 数据处理 / 原型）；
- **C/C++ 是底层工程观察与实现工具**；**不要求为了「更底层」而主动使用它**。

**降层流程（遇到无法解释的工程问题时）**：

```text
发现问题
  -> 当前抽象层能解释吗？
       能   -> 在当前层解决（结论可能仍然是改 Python）
       不能 -> 降低一个抽象层（runtime / library / OS / 进程线程 / 内存 / 系统调用 / 二进制 / ABI）
                 -> 能解释吗？ 能 -> 找根因；不能 -> 再降一层
```

**被隐藏 ≠ 不存在**：`list.append(x)` 看起来只是"往列表加一个对象"，背后仍然是对象 → 引用 → 内存 → 分配器 → 缓存 → CPU → 进程地址空间 → OS → 硬件。

**必须避免的两种错误**：

1. **无限叠加高层补丁**：`Exception A -> Patch 1 -> Bug B -> Patch 2 -> Bug C -> …`（bug 套 bug，最终一个错误的高层假设被十几个修补掩盖）
   —— 正确做法是**降低抽象层级找根因**，而不是继续 patch；
2. **把语言当解药**：Python 出问题 → "用 C++ 重写" ✗。修复层级应是**能表达根因的最低必要层**（很可能仍是 Python）。

**触发降层的信号**（高层证据不足时）：性能异常 · 内存暴涨 · 资源泄漏 · 死锁 · 数据竞争 · 崩溃 · 随机/极难复现的错误 · ABI 与平台差异。

**与治理链同源**：这与本包的 `状态 → 证据 → 门禁 → 审计 → 恢复` 一致 —— **不要用抽象掩盖未知**。
## 12. Language Addition Principle（语言新增红线）

新增一种语言 = **Adapter + Probe + 少量语言特化**；**绝不等价于新增一套 Skill**。

**三步提问（顺序不可颠倒）**：

1. **能复用 Core 吗？**（状态 / 证据 / 门禁 / 审计 / 恢复 / 交付是否原样可用）→ 能 → **只写 Adapter / Probe**；
2. **这是「该语言的工具差异」还是「新的工程维度」？**
   - **工具差异**（构建方式 / 测试框架 / 探针命令 / 工具链）→ **在 Adapter 内解决，Core 不动**；
   - **新工程维度**（现有抽象**覆盖不到**的约束，如所有权与生命周期、host-device 边界、内存模型）
     → 允许**小幅进 Core**，但必须三条同时满足：
     ① **不只为一种语言服务**（能被其它语言复用）；② **可机检或有明确人工判据**；③ **总量受限**（数量级为 KB，不是章节级）。
3. **需要显著扩张 Core 吗？**（`SKILL.md` / `workflow` / `code-quality` / `code-style` / 状态模型）
   → **是** → **暂停扩展，先审视 Core 的抽象是否漏了东西**（不要先怀疑语言）。

**红线（判据）**：支持一门语言若需要**显著扩张核心文档**，通常**不是这门语言太复杂，而是 Core 的抽象出了问题**。

**反例（不许发生）**：`Python Skill + C Skill + C++ Skill + Rust Skill + …` —— 那等于每加一种语言就把 Core 复制一遍。

**判据边界（防止红线变成教条）**：第 2 步必须先分「工具差异 vs 新工程维度」——
**后者是允许进 Core 的**（否则会误杀掉如"内存安全/所有权"这类**真实新增**的工程维度）。
### Provider 适配器（**薄**，不属于 Core）

成熟工具的输出格式不统一，Core **只认一种 JSON**：

```text
cppcheck --xml / clang-tidy YAML / lizard 文本
        ↓  （一个极薄的适配器，20 行以内）
统一 JSON lines：{"file":…,"func":…,"eff_lines":…,"ccn":…,"nest":…}
        ↓
code_metrics 的 judge（Core，不认识任何工具）
```

**为什么要这样**：Core 一旦开始解析各工具的原生格式，就会变成"第二套分析器"——**违反本包红线**。
适配器可以放在项目里（`tools/` 或 `scripts/local/`），**不进本包**。
**未接适配器时**：输出 0 条 JSON -> **明确待核**（指名原因），**不是静默通过**。

## 13. 语言差异表（**哪些指标需要语言化**）

> 原则：**语义统一、度量适配**；**不为"看起来整齐"而把一套数字复制成三套**（那是配置爆炸）。

| 指标 | Python | C | C++ | 是否需要语言化 |
|---|---|---|---|---|
| 函数有效行 | AST 精确可测 | 需工具 | 需工具 | ⚠️ **仅在有证据时** |
| 文件有效行 | 可测 | 可测 | 可测 | ⚠️ 同上 |
| 圈复杂度 | AST | 需工具 | 需工具 | ⚠️ 同上 |
| 嵌套深度 | AST | 需工具 | 需工具 | ⚠️ 同上 |
| 注释密度 | 定义不同 | 定义不同 | 定义不同 | ⚠️ 不宜机械统一 |
| **资源生命周期** | 运行时承担多 | **核心指标** | **核心指标** | ✅ 语言能力（Adapter） |
| **内存安全** | 语言机制较多 | **核心指标** | **核心指标** | ✅ 语言能力（Adapter） |
| **编译/链接警告** | 弱 | **核心指标** | **核心指标** | ✅ 语言能力（Adapter） |
| **ABI / 二进制兼容** | 通常非核心 | **核心指标** | **核心指标** | ✅ 语言能力（Adapter） |

**读法**：右列 ✅ 的，**不是"阈值不同"，而是"Python 版根本没有这项能力"** —— 它们属于 Adapter 能力，不进 Core 阈值表。
右列 ⚠️ 的**默认沿用同一组出厂阈值**；只有当真实项目数据证明"同一数字在该语言下判错了"时，才新增**按语言覆盖**（并在 `version-boundaries` 记录理由）。
### 语言准入判据（按**补充的工程能力**，不按市场使用率）

```text
底层控制与资源管理    C / C++ / Rust        内存 · 指针 · 数据布局 · 生命周期 · 硬件交互
并发与网络服务        Go / Java / Python    并发调度 · 服务生命周期 · 网络 · 分布式
Web 与应用平台        JS / TS / C# / PHP    浏览器 · 应用逻辑 · 服务端业务
移动与跨平台          Kotlin / Swift / Dart 平台 API · 生命周期 · 构建发布
```

（这是**工程能力分组**，不是互斥分类 —— 如 Rust 也能写 Web 后端。分组用于**判断准入理由**，不用于给语言贴标签。）

**每个候选语言必须回答两个问题**：

1. 它提供了**什么独特的工程能力**（其它已支持语言**不容易替代**的）？
2. 它**最容易出现哪些其它语言不容易出现的问题**？我们的质量体系**如何识别**这些问题？

**准入分两类，务必分清**：

- **语言适配器**：有**独立工程能力与风险模型**（Python / C / C++；未来的 Go：goroutine 泄漏 · 数据竞争 · context 取消传播；Rust：unsafe 边界 · 生命周期 · FFI）；
- **技术资产检查器**：不是语言，是**资产格式**（HTML / CSS / SQL / Bash / PowerShell / YAML / JSON / Dockerfile）—— 按**检查器**对待，**不按语言**对待。

**红线**：**不是每种语言都必须有自己的 collector**。成熟工具已能可靠提供的检查 → **接入并验证那个工具**，**不重造轮子**；
本包**永不**自己实现解析器 / 借用检查器 / 编译器（与 §12 主文、§9 一致）。


## 附：入口下沉内容（自 SKILL.md 入口下沉，2026-10-02。入口只留路由。）

> **语言层级原则（改变思考路径，不是语言排行）**：
> **抽象层级越高，被隐藏的系统状态越多；被隐藏 ≠ 不存在。**
> · **Python** ＝ 默认的**高层实现**工具（表达快、抽象高）——**不因引入 C/C++ 就动不动写 C/C++**；
> · **C / C++** ＝ **低层工程观察与实现**工具：当根因可能位于 Python 抽象层以下时，用它把**被隐藏的状态**暴露出来；
> · **何时降层**：性能异常 / 内存暴涨 / 资源泄漏 / 死锁 / 数据竞争 / 崩溃 / 随机或极难复现的错误 / ABI 与平台差异 → **主动降低一个抽象层级**再看（内存 · 资源生命周期 · 线程/进程 · 系统调用 · 数据布局 · 编译/链接 · ABI · 运行时 · 依赖 · 工具链 · 平台差异）；
> · **反面**：**不得**用"再加一层 workaround"掩盖未知，**更不得**把"Python 出问题"直接升级成"C++ 重写"——修复层级应是**能表达根因的最低必要层**（很可能仍是 Python）；
> · **目的**：**防止 AI 把高层语言的抽象误认为系统的真实状态**。细则见 `references/language-adapters.md` §11。

## 语言适用性路由表（封闭表：语言有限，行数封顶）

**用途**：AI 写某种语言时，一眼知道该找哪条质量要求、哪条不适用。

### 读取成本契约 RC1–RC4（**单任务认知半径不得随语言数量增长**）

| 条 | 契约 | 判据 |
|---|---|---|
| **RC1** | **单语言任务只读该语言所需子集** | 不读其它语言的 `adapters/` 附录与规则 |
| **RC2** | **一跳可达** | 由本表一行给出「该读什么」，不得要求遍历目录 |
| **RC3** | **未接线语言不读任何模型** | 直接答「未接线 → `[待核]`；**不适用 ≠ 不合格**」 |
| **RC4** | **入口只留路由** | 细则下沉后**必须在本表登记** |

> 机器载体：本表 ＋ `scripts/gen_views.py` §14 可发现性 ／ §11 引用完整性。

**机器侧真相**在脚本注册表里（本表须与之一致）：
`scripts/code_metrics.py` 的 `COLLECTORS` / `PENDING`；`scripts/known_defects.py` 的 `CODE_CHECKERS` / `PENDING_LANGS`。

| 类别 | 项 | 状态 | 度量 / 检查器 | 规模阈值 | 该读什么 |
|---|---|---|---|---|---|
| **语言 · 已接线** | Python | ✅ 已接线 | `code_metrics.py` + `correctness_rules.py`（C1/C2 阻断 · C3 观察） | **观察**（不阻断） | `code-quality.md` 全文 + `code-style.md` |
| **语言 · 已注册未接线** | C · C++ | 未接线（探针只返 `tbd`） | 探针 Provider（MAP 声明 -> JSON lines） | **不适用** | `code-quality.md` §0.2 + **`adapters/c.md` / `adapters/cpp.md`**（工具映射 + **来自标准的已知缺陷集**）+ 本文件 §6 / §9 |
| **语言 · 未接线** | Go · Java · JavaScript · TypeScript · Rust | 未接线 | 无（`PENDING_LANGS`） | **不适用** | `code-quality.md` §0.2 |
| **语言 · 未接线** | Kotlin · Swift · Dart · C# · PHP · Ruby · Lua | 未接线 | 无（`PENDING_LANGS`） | **不适用** | `code-quality.md` §0.2 |
| **技术资产（不是语言）** | HTML · CSS · SCSS · XML | 未接线 | 待接入（HTMLHint / Stylelint） | **不适用** | 本节下方说明 + 本文件 §12 |
| **技术资产（不是语言）** | SQL | 未接线 | 待接入（SQL linter） | **不适用** | 同上 |
| **技术资产（不是语言）** | Bash · PowerShell | 未接线 | 待接入（shellcheck / PSScriptAnalyzer） | **不适用** | 同上 |
| **技术资产（不是语言）** | YAML · JSON · TOML · Dockerfile | 未接线 | 待接入（各自成熟 linter） | **不适用** | 同上 |
| **数值 / 科学计算 · 已准入** | Fortran · MATLAB · R · Julia | **已准入（L0–L2）· 未接线** | 未接线（本机工具待发现 -> `[待核] provider unavailable`） | **不适用** | 本文件 §12 准入判据 + 下方「准入两问的答复」 |

**技术资产为什么单列**：它们**不是语言**（包内 §12 原文：按【检查器】对待，不按【语言】对待）。
套 CCN / 嵌套 / 长度就是**误用** —— 它们该用另一套维度（标记与样式语义 · 可访问性 · 注入 · 查询集合语义 · 脚本幂等），**尚未建立**。

**数值 / 科学计算语言：已准入（L0–L2）· 未接线** —— 两问答复（准入**必须留书面理由**；`plan §2` 十级**任何一级未完成即仍为 TBD**）：

| 语言 | ① 独特工程能力 | ② 其它语言不易出现的问题 → 如何识别 |
|---|---|---|
| **Fortran** | HPC / 数值内核（数组语义 · 列主序 · 高性能） | 隐式类型 · 整数溢出 · **列主序混用** · 越界 · 精度假设 → `gfortran` 诊断 + `-fcheck=bounds` + `-Wall -Wextra` + `-finit-real=snan` |
| **MATLAB** | 数值原型 · 矩阵生态 | **1-based 索引** · 列主序 · 隐式扩展 · 浮点 `==` · 未预分配致性能塌陷 → `mlint` / `checkcode` |
| **R** | 统计建模与可视化生态 | **NA 传染** · 因子与字符混用 · **`T` / `F` 可被覆盖** · 1-based 索引 → `lintr` |
| **Julia** | 高性能动态数值（多重分派 / JIT） | **类型不稳定致性能塌陷** · 全局变量 · 1-based 索引 · 浮点判等 → `--check-bounds=yes` + `JET.jl` / `Aqua.jl` |

★ **准入 ≠ 支持** ✓：上表只表示**允许进入 L0–L10 阶梯**；本机未发现 `gfortran` / `mlint` / `Rscript` / `julia` → **一律 `[待核] provider unavailable`**。
★ **`.m` 消歧（准入 MATLAB 的前置）** ✗：`.m` **同时是 MATLAB 与 Objective-C** —— 规则：**项目声明优先**（MAP 记 language）；**未声明即 `[待核] ambiguous`**，**不得默认判为其中任一**。
➡️ 工具接入时**不得**修改 `config/defaults.yml`、**不得**建语言专属阈值（`language-quality-adaptation-plan.md` §8）。

**技术资产为什么仍不按语言对待**：见本节上方说明（按【检查器】对待）。原判据「**答不出② → 现在就不加**」对**未准入**者仍然有效。

**接入一种新语言只需两步**（缺陷驱动，顺序不可颠倒）：

1. **先收该语言的已知缺陷** -> 加进 `scripts/known_defects.py` 的 `DEFECTS`（`lang` 填语言名）；
2. **再写检查器** -> 在 `CODE_CHECKERS` 加一行映射，并把该语言从 `PENDING_LANGS` 移出。

> 在完成第 1 步之前，**不要写规则** —— 先写规则再找缺陷，就是自娱自乐。
> 新增语言**不需要新增文件**：只在这张表加一行 + 在脚本注册表加一行。
