# 代码风格与工作方式（Code Style）

> **定位**：技能包协议正文之一（`references/`）。与 `references/code-quality.md` 的**分工按判据形态**划分：
> - `code-quality.md` —— **门禁与判据**：有阈值、可机检、违反即打回（机检实现见 `scripts/code_metrics.py`）。
> - **本文件** —— **风格与工作方式**：**靠人读与约定**，无统一阈值，评审时对照。
> **级别**：`[强制]` 违反即打回｜`[推荐]` 默认执行，偏离须写明理由｜`[参考]` 视场景选用。
> **两者都会出现 [强制]**：级别说的是"违反的后果"，**不是"能不能机检"**——不要把它当成分级依据。
> **可单独使用**：本文件与 `code-quality.md` 可以只带走一本（只要风格约定时不必装机检脚本）。
> **单独使用时的能力边界**（哪些门禁会失效）见 `MANIFEST.md` 的「子能力与最小集」。

---

## S1 命名规范


- **[推荐]** 命名机制通用、**具体风格由语言适配器给出**（本文件不写语言专属风格）：默认风格 + 白名单 + 禁止项三段式。
- **[强制]** **白名单机制**（可豁免默认风格的三种情况）：① 第三方库与框架约定；② 行业通用缩写；③ 历史遗留代码（为保持文件内部一致性可沿用原有风格）。
- **[强制]** **禁止**：拼音与英文混合、直接使用中文命名、完全不规范的缩写。
- **[推荐]** 标识符用英文（名字给机器和搜索），注释用**项目约定语言**（注释给人）——两者职责不同，不因统一而牺牲可检索性。**本规范下＝中文**（口径唯一，见下条 [强制]）。
- **[强制]** **语言口径（唯一一套，不留两套）**：**标识符用英文，注释与理由用中文**。
  ① **注释一律中文**——它给人读，本项目的人读中文；中英混排会让人在两个语系间切换；
  ② **标识符一律英文**——它给机器与搜索；中文命名破坏可检索性（见上一条禁止项）；
  ③ **豁免理由、提交信息同用中文**，与空话黑名单（code_quality.exemption.hollow_words）语种一致——**判据与语料同语种，才不会出现"拦不住"的盲区**。
> **语种盲区（必须显式化）**：`hollow_words` 出厂只收中文词；项目若改用英文注释/豁免理由，**英文空话不会被拦**。
> 要用英文理由，项目须自行扩 `hollow_words`（同步 `config/defaults.yml` 与 `scripts/code_metrics.py` 的 FALLBACK_HOLLOW，两处须逐键一致，由 `gen_views` §6 校验）。
  **不做多语种**：不是排他，而是**没有语料就无法验证**——定一个覆盖不到的标准，比不定更坏。
  ⑤ **状态声明**：语言口径由项目配置声明（默认 `documentation_language: zh-CN`）——注释/理由/提交描述用中文，标识符用英文；
     切换语言须同步扩 `hollow_words`，并保持 `config/defaults.yml` 与 `code_metrics.py` 兜底逐键一致（由 `gen_views` §6 校验）。

- **[强制]** **一套大小写风格必须由项目声明**：「默认风格 + 白名单 + 禁止项」的**语言专属细则由 `adapters/*.md` 给出**（见上条），
  项目须在 **MAP 规则段**声明本项目采用哪一套；**同一标识符的大小写变体不得并存**（`getUserID` ↔ `get_user_id` ✗）
  —— **模块名 / 文件名 / 配置键**同样适用（Linux 大小写敏感，Windows 静默合并）。
- **[强制]** **代码与配置面标点一律半角 ASCII**：**全角空格（U+3000）在禁止之列**（任何位置 ✗，它与半角肉眼无别）；
  注释与文案里的中文标点不受限。机检见 `scripts/gen_views.py` §16「配置面 ASCII 与全角空格」。

## S2 版面与可读性 [推荐]

- **[推荐]** **文件解剖顺序**：模块 docstring → imports 三组（标准库 / 第三方 / 本项目）→ 常量 → 主类主函数（辅助沉底）。
- **[推荐]** **辅助函数判据（一句话即可）**：辅助函数指主要用于支撑主体流程、**无需单独作为业务入口理解**的函数；判断依据是**阅读者的理解成本**，而非访问权限或调用次数（私有函数也可能是核心业务）。
- **[推荐]** **横幅分节**：类内方法按「构建 / 事件 / 业务 / 工具」分节——一眼看得出结构。
- **[推荐]** **函数三段式**：docstring → 守卫子句早返回 → 主逻辑分块，每块一行 why 注释。
- **[推荐]** **三问三答**：文件干嘛→docstring；函数干嘛→签名 + docstring；为什么这么写→why 注释。**美观即秩序感**。


## S3 抽象与复用 [推荐]


- **[强制]** **不过早抽象**：不引入不必要的设计模式，一层能解决的不拆成两层；**禁止为抽象而抽象**——拆分后子函数无法独立理解就不该拆。
- **[推荐]** **重复代码提取**触发线见 `{{config:code_quality.reuse.extract_threshold}}`（示例配置默认值见 `references/code-quality.md` §9）。与「不过早抽象」的张力按语义消解：结构**完全相同** → 达触发线即提取；仅**语义相似**而业务含义不同 → 并入重构回合观察，确认演进方向一致再提取（强行提取会导致后续修改互相影响）；跨模块的巧合重复 → 保持独立；性能敏感路径 → 内联展开优先。


## S4 重构策略：三阶段回合 [推荐]


- **[推荐]** 遇到超长、深嵌套、高复杂度的代码：**先完整写出逻辑，再分阶段重构**，顺序不可颠倒——第一阶段**提取重复代码**（先消除重复，否则拆出的子函数会各自带走一份重复）；第二阶段**拆分超长函数**（重复消除后拆，边界才稳定）；第三阶段**调整模块边界**（单函数问题解决后，才看得清模块级错位）。
- **[强制]** 每阶段重构后必须运行测试验证（`references/code-quality.md` **§7**）；重构须先声明范围与影响面（同上 **§5**）。
  （**依赖标注**：本条为必要依赖——单独使用本文件时，上述两条判据不可执行。）
  - **[强制]** **重构回合的测试分级（避免「全量测试」杀死流程）**：阶段①跑**受影响模块**的测试；阶段②跑**所在模块**的测试；阶段③跑**全量/完整测试链**。项目若无分级测试，则执行**已有的最高覆盖**测试，并在简报中声明该事实。
- **[强制]** 回查中被判定为**设计债**的豁免条目排入本流程；聚集度分析指向模块边界问题的直接进第三阶段（`references/code-quality.md` §2.3）。

- **[强制]** **算法与性能纪律**（自研禁区 / 先测后优 / 复杂度红线）是**可机检的判据**，归 `references/code-quality.md` §8——**不在此重复**（同一规则两处出现即为漂移起点）。


## S5 范例库与项目标杆文件 [推荐]


> 范式库机制与「标杆文件」指引是**同一机制**：一个给可抄的成品，一个给抄的对象。
> **操作面**（索引表模板 / 入库流程 / 分区规则）见 `examples/README.md`。

- **[强制]** **两个分区必须分开存放**：`examples/project/` ＝ **本项目的范例**（可信度来自「在本项目跑过、被评审过」，可当模板抄）；
  `examples/external/` ＝ **外部参考**（别处看到的好代码，可信度只来自「别人说它好」）。
  **外部参考必须登记来源与许可（#人检），状态恒为「参考·未验证」，不得当模板**；要当模板，唯一路径是改写进本项目、过流水线与评审后**作为 project 条目重新入库**。
  分开的理由：混放等于把**未验证的东西**标成项目标准，下一位无从分辨哪条能抄、哪条只能看。
- **[推荐]** **写前查范例**：动手写函数前先查范例库索引表，找场景匹配的范例并参照其结构、命名与注释风格落地；**无匹配场景**再按本规范自由发挥。**分层使用**：能力一般的执行者**严格参照**范例，能力较强的执行者以范例为**风格锚点**、无匹配场景时不必强行套用。
- **[推荐]** **项目标杆文件**：项目可指定现役标杆文件，并在任务简报中指明——**风格是「抄会」的，不是读规范会的**。
- **[强制]** **入库标准与更新**：范例必须通过流水线检查与代码评审后才可入库；文件头用注释写明「适用场景 / 关键技法 / 为什么它好」并按索引表头部约定登记场景标签；**一场景一范例**，出现更优写法时**替换**旧条目；随被淘汰的写法同步清理。
- **[推荐]** **范例要短**（以能一屏读完为度，超过即怀疑场景太大，拆分后只入库核心片段）；**入库的是「模仿对象」不是「查询对象」**——沉淀函数该长什么样的封装形状（契约、防御、豁免写法），不收入算法本体（算法推导可查教材且会过时，抄内核易语境错配）。


## S6 提交信息（Conventional Commits）[推荐]


- **[推荐]** 提交信息遵循 Conventional Commits 格式（类型前缀 + 描述，如 `feat:` / `fix:`）。理由：提交历史是变更意图的可检索记录，规范化的类型前缀让「这次是功能还是修复」不必读代码即可判断。
- **[推荐]** **语言**：类型前缀用英文（工具链依赖），描述用**中文**（与 §S1 ③ 一致，口径唯一）。
- **[推荐]** **豁免场景**：合并提交（版本控制工具自动生成）、紧急热修复（生产事故抢修，先提交后补规范）、流水线自动生成的提交（如版本号抬升）。
