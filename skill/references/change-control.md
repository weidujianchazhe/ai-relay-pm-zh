## 0. 第一原则：先分清"坏耦合"与"好耦合"

> **不是所有耦合都该解耦。** 有些耦合是**功能之间的相互约定**——解耦会直接破坏功能。
> 重构中最易发生的错误，是把「功能契约」当作「冗余」删除。

| 类型 | 判据 | 处置 |
|---|---|---|
| **偶然耦合**（accidental） | 同一事实被**抄写**到多处，靠**人工**保持一致；没有任何机器读它 | 可解耦 |
| **功能契约**（intentional） | A 的存在是因为 B 要读它；**改 A 必须同步改 B**，否则功能坏掉 | **禁止解耦**，且必须登记进 §D |

**一句话判据**：
> **「需靠人记住去同步」者为坏耦合；「机器读得到、改一处必须改另一处」者为好耦合——后者须保留，且须登记在案。**

> **推论（实战得出，两轮减量验证）**：**强耦合常常就是省成本的设计**——它把读取与校验压到最低。
> 所以**减量或解耦前，必须先证明它不承载功能**：§D.3 的「有意重复」（不同读者各读一遍）与 §D 的「功能契约」都属此类，
> 看着像冗余，实则是约定。**反过来，「不读就不付费」的按需内容也没有减量收益**——删它省不到路径成本，却让需要它的读者失去入口。
> 并且**「引用完整性」不等于「可发现性」**：文件存在 ≠ 读者找得到——删改路由后，必须由 `gen_views §14` 证明每个条目仍可被发现。

### 已知的功能契约（禁止解耦清单）

| 契约 | 为什么不能解耦 |
|---|---|
| **产物字段名 / 块名**（「上次交接」「已提炼」「代码根路径」「涉及」、交接 6+1 块名） | 它们是脚本的**功能接口**，改名等于改脚本全部逻辑依据 |
| **MAP 规则段配置 ↔ 门禁脚本** | 脚本必须读**实例 MAP** 的值——每项目阈值不同；收进技能包默认值会破坏"可配"功能 |
| **指针链**（卡「上次交接」→ 记录「下一步」→ 索引 [接力]） | 这是"上次工作在哪"的传输通道，断了接手链路就断 |
| **索引镜像写（热区/冷区）** | 不是冗余，是**容灾**：热区行被移出时冷区仍保有 |
| **检查点 ↔ 编号规则** | 必要的**联动认知**：改编号必须同步改检查点，否则门禁失效 |
| **速查表 ↔ 细则** | 「高频规则必须就地可读，指针只兜低频细节」——删掉速查表即抬升上手成本 |
| **可选能力条款**（稳定 ID / 设计卡生命周期 / 协作模式 / 角色矩阵） | 它们是**能力开关**不是复杂度。解法是"默认关闭 + 按需启用"，不是删除 |
| **包内 `scripts/` ↔ 项目 `scripts/local/` 的分界** | 前者归技能包（升级覆盖）、后者归项目（升级不覆盖）。**把项目专属逻辑塞进包内脚本 = 下次升级即丢**；反向把通用检查留在 `local/` = 每个项目重造一遍 |

## A. 改造门禁（逐条核对，缺一不得动手）

1. **功能零损失**：只减重复副本，不减唯一信息——被削减内容的唯一正本必须仍然存在且可定位；找不到正本就保留原文。
2. **交叉影响检查**：改/删/简化任何协议内容前，先查它的**消费者**——scripts/ 下各检查脚本、其他协议条款、模板字段对它的引用。**字段名/块名改名必须先 grep 全包列出同步清单**，逐处同步后才动手；局部简化若会断掉与检查/恢复/交接功能的配合，一律不做（实例见 §D）。
3. **上手成本不升**：接手路径文件（任务卡 → 记录 ±1 → STATE/MAP → 索引）只许变薄或等量、**不许净增**；内容指针化时**高频规则必须就地可读**（指针只兜低频细节）。
4. **成本归属三原则（快照 / 总账 / 分层）**：
   - **写路径恒定**：提交流程上的每个字段必须可**机械派生**（本地 list、单行查找、首句截取）。凡需全量盘点、全局扫描、跨目录统计的字段**禁止进入提交流程**——要费劲才能填对的字段早晚会填错，**错数比没有数更害人**。
   - **快照与总账分工**：STATE＝当前快照，索引冷区＝全量总账；累计统计（完成/废弃总数这类"期末余额"）归总账**按需查询**，禁止改回高频维护。改动允许把成本从高频路径移向低频路径，**禁止反向**。
   - **容量即封顶**：索引热区行数与 STATE 字数上限是接手默认阅读成本的**两处容量上限，不是可扩大的容量**——不得以"更完整 / 更全面"为由调大。超限时按快照纪律把历史段移入 reports/；要更多历史 → 按需读冷区。**分层结构（热区＝近期 / 冷区＝全量）不得合并。**
5. **权威源流程**：先改 `references/` 下对应正文 → 同步 `MANIFEST.md` 版本 → 运行 `scripts/gen_views.py` 重生成派生视图。**派生视图一律不手改。**
6. **改进先复盘**：改造动因与方案先记入工作区 `REVIEWS.md`（障碍→根因→建议→处置），再落地。

> **⚠ 冲突即提醒（强制义务）**：执行改造的 AI 发现拟议改动与上述任一门禁/契约冲突时，**必须主动向用户显式提醒**——
> 写明冲突的是哪条原则、改了会伤哪个功能、负担加在哪。**未经用户明确确认不得执行**；
> 也不得静默服从"照做就是"的指令，更不得静默放行绕过门禁。

### A.1 反屎山红线（[强制]）

发现一个新竞态时，**不允许直接加一个特殊判断**。必须先回答四问：

① 它违反了哪条**不变量**？  ② 哪一层**负责**这条不变量？  ③ 为什么现有 primitive **没有表达**它？  ④ 修 primitive，还是修业务逻辑？

**若答案落在「这里加一个 if」，视为红灯。** 优先**删机制**而不是**加机制**
（范例：把 `unlink` 从释放路径里整个删掉，而不是再加一个 token 判断——净减代码，窗口结构性消失）。

**层界（配合本红线）**：平台细节 `flock` / `msvcrt` / `O_EXCL` / `epoch` / `inode` / `fd` / unlink **只允许出现在 `scripts/locks.py`**；
业务侧只经 `lease.exclusive_resource(path)` 进入临界区，不得 import `acquire_lock` / `release_lock` / `verify_lock`。

**冻结清单**（不再为它们增加任何机制）：多文件 all-or-nothing · 跨机/分布式互斥 · NFS/SMB 建议锁 · 证据真伪。

> **改核心前的八问（摘要）**：① 原始证据是否仍可追溯 ② 是否新增第二套写入口 ③ 是否新增第二套 ownership/lock 语义 ④ 是否把声明当成证据 ⑤ 是否从明确失败变成静默降级 ⑥ 是否新增复杂状态机 ⑦ 是否增加核心上下文成本 ⑧ 能否在核心之外实现。
> **默认答案：能在核心之外实现，就不要进入核心。**（八问任一为「是」，先按红线处理，不得直接进核心。）

## B. 不变量（invariants — 禁止删除 / 弱化 / 改语义）

1. **记录指针链**：任务卡「上次交接」→ 记录「下一步」→ 索引 [接力] 行 +「交接文件」列——上手成本恒定的承重墙。
2. **索引镜像写**：热区 N 行 + 冷区全量，行永不丢失（**移入不删除**）。
3. **每篇记录最多被读一次**：读后增量**写回**任务卡——同时是误删容灾层（读过的已回卡）。
4. **档案只进不出**：AI 不删/不移 `reports/` 与 `archives/`（唯一例外＝归档流程，移后必须同步索引行指向）。
5. **数据诚实边界**：恢复不出的内容标「数据待补」，**禁止伪造**。
6. **审计/恢复依赖清单**：交接 6+1 块名、任务卡稳定 ID/「上次交接」「已提炼」「代码根路径」「涉及」、revision/hash/CAS 元数据、MAP 的 ID 注册与配置项——**这些是检查脚本与恢复脚本的功能接口，不是协议复述，瘦身刀不落此处**。
7. **版本权威源与派生视图一致**（由 `gen_views.py` 校验）

## C. 记录与恢复保障

- **改动记录三层分工**：MAP＝结构账本（新路径/新分支）· reports＝改动摘要账本（有 git 时附 commit hash）· 索引＝指针账本（镜像写永不丢）——**内容准确性的源头在 reports**。
- **MAP 路径注册表对账**：校验注册表路径存在性——手动移动/改名目录后必须更新 MAP，防"地图静默过时"。
- **备份方式登记**：MAP 环境段登记备份方式（git / 定期复制 / 无）——整目录误删超出协议恢复能力，靠备份兜底；协议只登记不实现。
- **源包对照还原**：多记录互证，**对的是一致性，不是直接还原信息**——源包受损时 ① 从任一项目工作区逐字对照还原协议正文（工作区随带 `references/` 逐字副本，故正文亦可还原；旧版工作区只带 `SKILL.md`，正文走 ②）；② 无工作区副本的按备份方式取回，取不回的标「待补」**不伪造**；③ 还原后跑版本一致性校验、恢复动作记 `REVIEWS.md`。

## D. 强耦合警示（每次改动必读）

> **本技能没有孤立的协议行。** 很多单项功能表面只占几行，实际是多个功能点的交汇节点——
> 删掉或改写"几行字"，断掉的是别处正在运转的功能链。**每一次改动先看实例、再过六问，慎之又慎。**

### D.1 耦合实例（看似几行，实为节点）

| 表面看起来 | 实际承载 |
|---|---|
| MAP 规则段配置行（索引行数 / STATE 字数上限 / reports 归档阈值 / 检查开关 / 协作模式） | 索引截断、STATE 封顶、reports 归档、审计开关等功能的**运行依据** + 一致性校验的对账输入 |
| 索引头部「行数标注话术」（1 行指针） | 冷区断点提示功能的行为来源（话术正本在协议正文） |
| 任务卡「上次交接」字段（1 行） | 接手链入口 + 指针有效性校验 + 断链修复对象 |
| 交接 6+1 块标题（7 行） | 提交流程门禁的**逐块校验对象** |
| STATE「字段级更新」（1 行） | 并行提交不冲突的保证 + 门禁的 STATE 证据项 |
| 索引编号规则（2 行） | 索引校验的**全部逻辑依据** + [接力] 链跨归档续接 |
| 管理区文件清单（`references/artifacts.md` §1 的十几行） | **三处同步**：`scripts/validate_workspace.py` 的 `REQUIRED_*` 常量、`README.md` 初始化步骤、`templates/MAP.template.md` 路径注册表——**增删一行要三处同改** |

### D.3 有意的跨文件重复（**不得以"去重"为由删除**）

**判据**：**同一读者读两遍＝冗余；不同读者各读一遍＝分工。**
只有一种重复必须消除：**第二份"真值"**（数值副本、模板副本、版本副本）——那会漂移。
下列重复属**有意的分工**，删掉它就是让某一类读者失去入口：

| 重复 | 读者 |
|---|---|
| 「脚本一览表」（`scripts/README.md` · `SKILL.md` · `references/README.md` · `BLUEPRINT.md` 各一份） | 跑脚本的人 / 接手者 / 选型者 / 看蓝图的人 |
| 「四类审计锚点表」（`references/audit.md` 与本蓝图） | 执行者 / 只读蓝图的人 |
| 「边界声明：不做实时监督」（`SKILL.md` · 蓝图 · `BLUEPRINT.md` · `references/onboarding.md`） | 使用者 / 改造者 / 选型者 |
| `references/glossary.md` §三「旧名对照」 | **持有存量工作区的人**（包内 0 引用不等于无用） |
| 速查卡 ↔ 细则（`references/cheatsheet.md` ↔ 各正文） | 任务简报随附 / 深读 |

> **删除这类内容前必须先回答**：删掉之后，**哪一类读者要靠什么才能拿到同一条信息？**
> 答不上来就保留——**"包内 grep 0 引用"从来不是删除理由。**

### D.2 改动前六问（答不全就停下）

1. 这几行被 `scripts/` 下哪些检查/恢复脚本当作输入或校验对象？
2. 被哪些模板当作字段或块名引用？
3. 被哪些派生视图与协议其他节引用？
4. 改后原本依赖它的每个功能，是否仍有**等价路径**完成任务？
5. 接手 AI 会不会因此需要读更多东西（上手成本是否上升）？
6. 同步清单是否齐备、改动记录是否已写 `REVIEWS.md`？

**纪律**：答不清"谁在消费这几行"就不改；改动**宁小勿断**——宁可多保留一行看似冗余的协议，不可断掉一环正在运转的配合。

## E. 审计思想（设计原理 · 改编号/时间戳/引用/凭证相关协议前必读）

> **分层原理**：文档协议**不做、也做不到实时监督** AI——监督是 `scripts/` 层的职责（皆为确定性函数）。
> 文档层的任务是**事后可审计**：每条声明至少有两个以上独立记录互证——疏忽、伪造、差错在审计时必暴露。
> **协议不为"AI 一定守规矩"而设计，为"不守规矩必留痕"而设计。**

> **反激励原则**：任何冲突裁决规则**不得给伪造留收益**。
> 教训：「跨分支以时间戳后写为准」＝「谁伪造时间戳谁赢」——**裁判规则作弊有奖即是漏洞**。
> 现行设计：时间戳仅作辅证、裁决归 MAP 登记的裁决者、撞号重试留痕——伪造无收益。

> **锚源原则**：**锚的值必须由被审计者之外产生。**
> 自报值（姓名、自取的名字、自编的短码）与声明**同源**，可任意填写且无从核实——**不构成锚**；
> 机器值（机器码、时钟时间戳、版本控制提交号）与声明**异源**——**方可作锚**。
> 已按此原则改造：**身份锚**（AI 标识 → `{平台}-{机器码}[@{角色槽}]`，由 `scripts/stamp.py --ai-id` 产生）、
> **人检标记**（`owner`/`next` → `slot` + `by` 机器戳，到期由戳推导）。
> 推论：**本层只出「哪台机器、何时」，不出「哪个人」**；定位到人是人工复核的职责。
> 违反此原则的改动（例如为"可读性"把机器值改回人名）**一律先过 §A 并向用户明示冲突**。

### 四类审计锚点

| 锚点 | 载体 | 暴露什么 |
|---|---|---|
| **时间锚** | 记录文件名日期 · 索引行日期 · 交接时间戳 | 倒序/时间倒退 → 可疑（辅证启发式，不作裁决） |
| **ID 锚** | 稳定 ID 创建后不可变，事件重试生成新 ID | 缺失回链 / 重复事件 / 非法状态 |
| **身份锚** | AI 标识 `{平台}-{机器码}[@{角色槽}]`（机器产生） | 冒名/混写 → 对照索引行与卡上承接 |
| **凭证锚** | 改动点 commit hash（有 git 时） | 谎称改动 → `git show` 对原始凭证 |

> **编号规则是审计接口，不是格式偏好**：改编号格式/递增规则/登记要求 ＝ 改索引校验的全部逻辑依据与 [接力] 链续接方式——
> 必须先过 §A 第 2 条（交叉影响检查），grep 全包列出同步清单后才动手。

> 完整设计蓝图见 `BLUEPRINT.md`。


## 新增规范前的四问 [强制]

任何新增（或收紧）规则前，提案必须逐条回答；缺一即不受理：

1. **解决过什么真实缺陷？** 指出实际发生过的、可复现的案例（无案例 = 先记录事实，不加规则）。
2. **能否被现有规则覆盖？** 若能，改现有规则的表述，**不要新增第二处真值**（同一规则两处出现即漂移起点）。
3. **是否增加执行成本？** 是，则说明该成本换取什么，以及能否用自动化抵消。
4. **是否需要自动化？** 需要则同时给出机检或自检的落地方式；不需要则写明由谁、在何时人工判断。

> 依据：**规范债务零存续**——用得上的留下、用不出的出清（见本文档既有元规则）。

## 项目级适配与技能源包隔离协议 [强制]

**核心原则**：**项目适配归项目管理区，通用能力归技能源包 —— 两者物理与职责隔离**。
**最终边界**：**实际项目可以适配技能，但不得擅自改造技能本体；项目需求与通用技能演进是两条独立的维护路径。**

| 问题来源 | 应当修改的位置 |
|---|---|
| 蓝图行数上限不适合当前项目 | **项目管理区协议**（`MAP.md` 规则段覆盖 `capacity.*`） |
| 项目需要增加特殊检查规则 | **项目管理区脚本**（项目侧，不写进源包） |
| 项目需要不同的验收标准 | **项目管理区协议** |
| 多语言项目需要额外检查 | **先做项目级适配**（Provider 薄适配器放项目侧） |
| **多个项目反复遇到同一通用能力缺口** | **独立评估技能源包升级**（见下 §4）——**不代表可把项目补丁复制进源包** |

1. **允许修改的范围**：仅**当前项目管理区**内的文件（项目协议与规则 · `MAP`/配置/索引 · 项目专用审计与检查脚本 · 项目专用模板与检查清单）。
2. **禁止修改的范围**：**不得因单个项目的实际需求，直接修改技能源包中的任何文件**（核心指令与管理规范 · `references/` `templates/` 等通用参考 · `scripts/` 及其通用工具 · `config/` 配置/清单/注册表）。
3. **适配原则**：优先通过**项目管理区的协议、配置和脚本**解决问题；**不得为了通过现有门禁而降低实际工程质量要求**；**项目特殊需求不得直接转化为全局通用规则**；项目级修改**不得反向覆盖、替换或污染技能源包**；管理区的修改应**保留修改记录、原因与验证结果**。
4. **通用能力缺口处理**：先在**管理区记录**问题、实际需求与证据 → 作为**独立的技能改进需求**提出 → 由**技能维护流程**单独评估、设计、测试和发布 → **未经独立维护流程，不得在项目执行过程中直接修改技能源包**。

> **既有落点（互指，勿重复定义）**：`code-quality.md` §0.2（未接线语言报 `[待核]`——那是**不适用**，**不要去"修"它**）· `config/providers.json` 的 `procedure` 第 4 步（**薄适配器放项目 `tools/`，不进本包**）· `tools/README.md`（**只放规范，不随包分发实现**）· `ci/README.md` §3（阈值取自**实例 `MAP.md` 规则段**，缺失才回落 `config/defaults.yml`）· `version-boundaries.md`（不能反向覆盖的清单）。
> **与本节上方「四问」的关系**：本协议本身按四问评估通过 —— ① 解决真实缺陷（项目侧误改源包 / 阈值被项目直接改掉）② **部分可被既有条款覆盖，故只补一条统一边界、不新增第二处真值** ③ 成本低 ④ 暂不需要自动化（属约定 + 留痕；如需可日后补机检）。
