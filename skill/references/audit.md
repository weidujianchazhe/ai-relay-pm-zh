# 审计与一致性（Audit）

> **何时读**：定期自检、收账复核、或怀疑"账实不符"时。
> **前提**：这些检查**已随包提供可执行实现**（`scripts/`），**不必手写**。
> 本文件说明**每个检查在查什么、为什么这么查**；具体判定逻辑以脚本为准。

---

## 1. 设计思想

> 文档协议**不做、也做不到实时监督** AI——监督是脚本层的职责（皆为确定性函数）。
> 文档层的任务是**事后可审计**：**每条声明至少有两个以上独立记录互证**——疏忽、伪造、差错在审计时必暴露。
> **协议不为"AI 一定守规矩"而设计，为"不守规矩必留痕"而设计。**

由此推出两条工程约束：

1. **每条声明要有第二读者**。只有一个记录说了的事＝不可审计。例：「声称已提交」必须能在
   索引里找到行、在文件系统里找到记录文件——**三者互证**。
2. **判据必须是确定性的**。凡需要"理解语义"才能判的，一律标 `[待核]` 交人或模型，
   **脚本不硬判**（避免误报掩盖真实问题）。

## 2. 四类审计锚点

| 锚点 | 载体 | 暴露什么 |
|---|---|---|
| **时间锚** | 记录文件名日期 · 索引行日期 · 交接时间戳 | 倒序 / 时间倒退 → 可疑（**辅证启发式，不作裁决**） |
| **ID 锚** | 稳定 ID / 分支码 创建后不可变；事件重试生成新 ID | 缺失回链 / 重复事件 / 非法状态 |
| **身份锚** | AI 标识 `{平台}-{机器码}[@{角色槽}]`——由 `scripts/stamp.py --ai-id` 产生 | 冒名 / 混写 → 对照索引行与卡上承接 |
| **凭证锚** | 改动点 commit hash（有 git 时） | 谎称改动 → git show 对原始凭证 |

### 2.0 立论：锚的值必须由被审计者之外产生

审计锚是否成立，取决于**该值由谁生产**：

| 值的来源 | 与声明的关系 | 可否作锚 |
|---|---|---|
| **被审计者自报**（姓名、自取的名字、自编的短码） | 声明与证据**同源**——填写者既是声明的发出者，又是唯一的证明者 | **不可**。可任意填写，无第二读者可核 |
| **机器自动识别或记录**（机器码、时钟时间戳、版本控制提交号） | 声明与证据**异源**——填写者不生产该值 | **可**。伪造需额外动作，而该动作本身留下痕迹 |

> **通用规则：凡由被审计者自行申报的标识，一律不得作为审计锚。**
> 锚只能取机器可自动产生的值——**机器码**（哪台机器）、**时间戳**（何时）、**提交号**（改了哪些字节）。

**人名为何尤其不可用**：其伪造成本为零，且伪造后与真实署名无法区分——
它提供的是「看起来有人负责」，而不是「可以追究到某个动作」。

**本层的边界**：机器码回答「哪台机器、何时」，**不回答「哪个人」**。
由「机器 + 时间段」定位到具体的人，是人工复核的职责（查机器清单、查该时段会话记录、查提交署名）。
协议层不承诺定责，只承诺留下可追溯的痕迹。

### 2.1 人检标记：只挂机器戳，不挂人名

**原设计的问题**：`#人检(owner=某人, next=某日)` 的两个字段均为自报值。
按 §2.0，二者都不构成锚。该设计还会自锁：

```
标注 #人检 → 无人实际执行 → 「未执行」不可见 → 晋升机制取不到计数 → 标注永久留存
```

该状态无需任何事故即可维持——它依赖的唯一通道（人的观察）已经关闭。

**改法**：标记只保留机器产生的值。

```
#人检(slot=<角色槽>, by=<机器戳>)
```

| 字段 | 含义 | 取值方式 |
|---|---|---|
| `slot` | 应由哪个**角色**执行复核 | 注册表取值：`config/defaults.yml` 的 `audit.human_check.slots`（列表，不适用占位符）。写人名无收益，它不是任何人的不在场证明 |
| `by` | 机器戳 | `scripts/stamp.py` 产生，人不填写 |
| `owner` | 已删除 | 自报人名，按 §2.0 不可作锚 |
| `next` | 已删除，改为推导 | 到期 = `by` 的时间 + `{{config:audit.human_check.period_days}}`。删除可伪造的输入，即删除伪造面 |

**戳的强度分档**（本标记的关键输出，不只是格式）：

| 档 | 戳形 | 产生者 | 写入者可否伪造 |
|---|---|---|---|
| **强** | `git:<短hash>@<ISO8601>` | 版本控制 | 不可，除非改写历史；而改写历史会留下痕迹 |
| 弱 | `host:<机器码>@<ISO8601>` | `scripts/stamp.py` | 可以。能写入文件者也能写入同形戳 |

> **锚的强度取决于它有多「不由写入者生产」。** 因此有版本控制时必须挂 git
> （`require_git_when_available` 默认开启）。此结论与 §3.4「越界改动」同源：
> **启用版本控制是投入产出比最高的一项基础设施**，它同时解锁凭证锚与本项强锚。

**该设计如何解除上述自锁**：判据由「人是否观察到」改为「戳是否更新」。

```
旧：标注 → 无人执行 → 「未执行」不可见 → 不晋升 → 永久标注   （依赖人的记账，通道已关闭）
新：标注 → 戳未更新 → 到期即判红                            （依赖时间戳，无需任何人配合）
```

**缺口由「没人看见」变为「时间戳未动」——后者是机器可直接读出的确定性事实。**

### 2.2 身份模型：四种身份，只有三种可用（第四种不采集）

评审常问「能不能识别出是哪个 LLM」。答案是**分层的**——别把四种身份混成一种：

| 身份 | 谁产生 | 本包怎么用 | 可否作锚 |
|---|---|---|---|
| **运行时** runtime_identity | **环境**（宿主环境变量 / 父进程名） | `stamp.py --evidence` 自动识别（如 `DSH` + 会话 id；或 `claude-code` / `cursor` / `codex`…） | **可**——环境产生，填写者不生产 |
| **机器** machine_identity | 程序（主机名 + 机器标识哈希） | `{平台}-{机器码}`，见 §2.1 | **可**（有 git 时为强） |
| **模型** model_identity | 三级来源（强度从高到低）：**宿主环境变量 → 宿主配置文件 → 模型自报** | `stamp.py --evidence` 自动探测前两级（实测本机读的是宿主配置里的登记值）；**都没有就留空**——绝不去问模型自己 | 宿主给的作**弱证据**（登记值 ≠ 本会话实际值）；**自报的不可** |
| **人** human_identity | 人 | **不采集**：标记里没有人名字段 | — |

**模型名为什么是"弱"证据**：宿主配置记的是**默认/已配置**的模型，而用户可能在会话里切换过——
所以它是"**登记值**"，不是"本会话实证"。**照录并标注来源，比不记或猜一个都强。**
落点用 `stamp.py --evidence --append` 把这一行追加进元数据通道。

**为什么不问模型自己**：模型说自己是什么是**自报值**——可任意填写、且填写者正是被审计者，
声明与证据同源，不构成锚（§2.0 的立论）。**留空比填一个不可信的值好**：空值至少诚实。

**实测（本机）**：环境里有 `DSH_HOME / DSH_PROFILE / DSH_SESSION_ID`，父进程链是 `DeepSeekHarness.exe → node → node → powershell`
——运行时与会话**识别得出**；而环境里**没有任何模型名变量**，模型身份**拿不到**，故留空。

**隐私边界（[强制] 提醒）**：机器码是**稳定标识**——同一台机器永远是同一个值。
因此**不要把长期累积的机器戳连同项目痕迹发布到公开仓库**：它会把"同一台机器的一串活动"关联起来。
要公开时择一：① 用仓库级别名参与公开记录（机器戳只留本地）；② 接受该风险并在 `MAP` 里显式登记（**登记过的取舍叫决定，没登记的叫意外**）。


### 2.3 拿不到模型名时怎么记（**降级阶梯 + 来源标签**）

不同底座给的线索不一样，**有的什么都不给**。所以不能只设计「拿得到」的路径——
关键是：**拿不到也要记成「拿不到」**，否则将来分不清「当时没记」与「当时确实拿不到」。

**五级降级（高 → 低）**，值必须**带着标签一起走**：

| 级 | 来源标签 | 谁能产生 | 强度 | 说明 |
|---|---|---|---|---|
| 1 | `[env]` | 宿主环境变量 | 弱偏中 | 机器值，最可靠的一档；仍非「本会话实证」 |
| 2 | `[host-cfg]` | 宿主配置文件 | 弱 | **登记值**：宿主记的是默认/已配置模型，用户可能切过 |
| 3 | `[human]` | 人在 MAP 里登记 | 弱 | 声明而非机器值；**换模型后必须改这一行，否则是过期声明** |
| 4 | `[self]` | 模型自报 | 弱（**不可作锚**） | 可伪造、且常记错版本；**显式标 self 是为了不让它混进事实** |
| 5 | `[absent]` | —— | — | **明确记「不可得」**，并给出补法（见下） |

**为什么值必须带标签**：值一旦离开标签，就变成了「看起来确凿」的假证据——这正是本包最防的形态。
留痕形态（元数据通道 REVIEWS.md）：

```
- 2026-09-26T22:18:13+08:00 · 运行证据 · runtime=DSH · provider=- · model=不可得[absent] · session=… · machine=host:11e1a541@…
```
**不可得时的补法（按强度）**：

1. **让宿主把模型名写进环境变量**——最强，且本技能无需改动即刻生效（探测顺序已含 `MODEL_ENV` 词表）；
2. **在 MAP 规则段登记一行** `- 底座模型：<名字>`——人登记（`[human]`），弱但可追溯；
3. **显式记一条自报** `--model-self "<名字>"`——**会标 `[self]`，不作锚**，仅作线索；
4. **什么都不写**：输出就是 `[absent]`，并说明两条补法。**留空而不猜。**

> 一条纪律：**不得为了让字段看起来完整而填一个模型名**。字段完整不是目标，**可追溯才是**。
**落点**：运行证据写**元数据通道 `REVIEWS.md`**（追加一行）；**不要塞进人检标记**——
标记里只放机器戳，塞别的东西会让格式校验失效（§2.1 的格式是机器逐字段校验的对象）。

## 3. 检查清单（对应 `scripts/`）

### 3.1 提交流程门禁 — check_closeout.py

- 最新记录是否 **6+1 块齐全**（块名精确字符串匹配）
- 「任务卡更新」块声明的归档任务卡，**目标文件是否真的存在**
- 索引是否已登记本次编号行
- STATE 是否已更新（时间戳 ≥ 最新记录）

> **为什么块名要精确匹配**：块名是**逐块校验对象**（见 `references/change-control.md` §D.1）。
> 写成近义词（如漏掉"本次涉及"四字）会导致门禁报缺块。

### 3.2 索引完整性 — check_index.py

- 编号格式（两位大写字母 + 4~5 位数字）；分支字母**已在 MAP 分支登记中注册**
- **同分支数字严格递增**（按**数值**比较，不是字符串比较）
- 类型标记 ∈ 四个合法值
- 「交接文件」列指向的路径**存在**（指针不悬空）
- 热区 + 冷区**镜像写一致**（热区截断属正常，冷区应全量）

### 3.3 一致性校验 — reconcile.py

**三方互证**（这是"每条声明要有第二读者"的落地）：

```
STATE.md（当前快照）  ↔  reports/（改动摘要账本）  ↔  INDEX（指针账本）
```

- 快照的"最近更新"时间 ≥ 最新记录时间
- 记录声明的改动点 ↔ 索引行的主题（不得一方有、一方无）
- 卡「上次交接」指针 ↔ 记录文件存在性
- 冷区累计行数 ↔ 实际行数（禁维护"每次提交都更新的计数器"）

### 3.4 越界改动检查 — 无脚本（条款保留，实现依赖 git）

> **为什么没有脚本**：判据是"实际改动的文件"与"任务卡「涉及」声明的范围"之差集。
> 无版本控制时只能靠 mtime 近似，**近似即不可靠**（本机实测：mtime 无法区分"刚被写过"与"正在被写"）。
> 因此本项**不产出确定性判定**，脚本层不做；条款保留，供有版本控制的项目落地。

- 输入：任务卡「涉及」字段（允许文件/目录清单）
- 有版本控制时：`git status --porcelain` / `git diff --name-only` 取实际改动 → **差集 = 越界**
- 无版本控制时：退化为 mtime 时间窗近似，结果**必须标注为近似**，不得据此问责
- 输出：越界文件清单；**这是"改了不该改的文件"的唯一确定性来源**

> **强烈建议**：管理工作区启用版本控制。它同时解锁本项检查与 §2 的**凭证锚**
> （改动点附 commit hash，`git show` 即得原始凭证），是投入产出比最高的一项基础设施。

### 3.5 工作区结构 — validate_workspace.py

- 必需文件/目录齐备（见 `references/artifacts.md` §1）
- MAP 路径注册表登记的路径**实际存在**（防"地图静默过时"）
- MAP 规则段配置项齐备且类型正确
- 字段名 / 块名无拼写漂移

## 4. 判定口径（三态，统一）

```
[通过]  PASS      确定性成立
[问题]  PROBLEM   确定性不成立 → 退出码 1，阻塞
[待核]  TBD       无法确定性判定 → 退出码 2，交人或模型
```

**信噪比纪律**（实践教训）：

- **常量 `[待核]` 必须消除**——设计上永久的待核项（如"无 git 故无法比对"）应降级为
  一行 `[建议]` 提示，**不得占用待核通道**。否则"退出码 0"永不可达，门禁信号失效。
- **已登记的豁免要机器可读**——豁免记在文档里而脚本不读它，会让已豁免项每次都报红，
  逼每个接手者手工分诊"这条红是不是我的"。
- **异常退出码必须计入结论**——脚本崩溃/段错误不能因为"用例都过了"就被算作通过。

## 5. 管理自检（定期 / 按需）

- [ ] 上手成本是否**无净增**（任务卡 → 记录 ±1 → 快照/地图 → 索引）
- [ ] 任务卡是否只留活跃？完成即归档、废弃留痕？
- [ ] 索引类型标记正确？`[接力]` 链连续？
- [ ] 提交流程分派是否执行？
- [ ] 人读区与 AI 区是否同步（无单边分叉）？
- [ ] 技能自身问题是否已记入 `REVIEWS.md`（元数据通道闭环）？
- [ ] 任务卡是否**覆盖式**（无滚雪球、无历史堆积在卡内）？
- [ ] 活跃卡卡尾是否含**提交协议速记**（协议钩子在位；旧卡写作「收工协议速记」，改名后再补——缺速记的卡多为旧卡或重建漏抄）
- [ ] **中断卡**处理：承接非「—」但进度锚点停在半途且长期未动 → 提示用户续作 / 改派 / 废弃
      （**废弃由管理者决定，AI 只提示**）
- [ ] 决策点是否已登记（快照决策点段 / 任务卡要点）？
- [ ] 稳定 ID（启用时）是否稳定且引用可追溯？
- [ ] 并发元数据（owner / revision / 内容哈希 / 原子写或 CAS）是否齐全？
- [ ] 当前模式的文件集、角色权限与升级条件是否满足？
- [ ] 废弃需求是否留痕（索引一行 + 原因）？
- [ ] 档案红线：记录与归档目录**无被删/被移文件**（被删时索引指针悬空 → §3.2 与恢复流程可发现）
- [ ] 归档是否**该触发未触发**（`reports/` 篇数已达 MAP「reports 归档阈值」→ 提交时应已归档）
- [ ] 完成卡是否已移入 `archives/done/`（完成型提交**不删卡**，保留记录）
- [ ] 存量项目的历史缺口是否已标「待按需整理」（**未深挖历史是设计如此，不是漏项**）

> 自检项**不设"必须达标"的硬指标**——凡无法兑现的指标只会形同虚设。
> 例：曾要求「上手成本恒定 ≈ 一张卡 ±1 记录」，在真实项目上不可能达标；
> 现行口径为**「无净增」**（只许变薄或等量）。

## 6. 开关与假账

**配置里写「定期排查：开」，不等于排查发生了。** 账面上有这项控制、实际不存在——这是**假账**。

### 6.1 两种开关，两种假账

| 开关形态 | 假账形态 | 例子 |
|---|---|---|
| **声明式**（配置里一个「开」字） | 开了没人跑；或跑了没人看 | MAP 写「定期排查：开」而元数据通道里从无核查记录 |
| **条件式**（满足某条件才报） | 条件永假 → 检查永不触发，恒绿 | 「有 git 才比对凭证」在无 git 工作区恒为绿 |

**共同点**：**判据取自「声明」，而不是取自「痕迹」。** 这与 §2.0 的锚源原则是同一条病。

### 6.2 修法：开关不是许可，是承诺

- **承诺由痕迹核实**：「定期排查：开」的兑现证据是 **`REVIEWS.md` 里带机器戳的核查记录**；超期即红，不看配置里那个字。
- **恒假条件必须显式降级**：条件不成立时不是「通过」，而是 `[建议]`（提示本项不适用）——**不得占用通过名额**。
- **开关的取值必须能被机器读出并解释**：写在文档里而脚本读不到的开关，等于没有开关（见 §4 信噪比纪律）。

### 6.3 落地

```
python scripts/audit_all.py <管理区>
```

一条命令跑完全部门禁，**并把结果以机器戳写回 `REVIEWS.md`**；下次运行时自查「距上次核查多久」，
超期或**从无记录**即报 `[待核]`。**「开了却没跑」会自己变红，不需要任何人记账。**

### 6.4 三处残余风险的处置（写死，防止"以为已经解决了"）

| 残余 | 处置 |
|---|---|
| 自动化**没有开关**（想手写就手写） | 归档与索引写入**只影响「谁来写」，不影响「写没写」**——人写的产物照样要过 `check_index` 与 `check_closeout`。**读不到也不生效的开关一律不保留**：宁可不承诺，也不要兑现不了的开关（见 `_common.BOOL_KEYS` 的说明）。 |
| 核查周期值只是 MAP 里的一个数 | 周期**只决定"多久算超期"**，不决定"查不查"。查没查由 REVIEWS 里的机器戳核实（§6.3）。**周期被改大只是把红线推远，推不没。** |
| 无 git 时人检戳只是弱锚 | 已在 §2.1 强度分档里**显式声明**，并由 `stamp.py` 主动提示「启用版本控制可升为强锚」。**不假装它是强锚。**

## 7. 全盘核查由谁读：脚本还是 AI

> 这是**成本与理解**的取舍问题，不是单纯的省钱问题。判据按**目的**分，不按成本分。

| 目的 | 由谁读 | 理由 |
|---|---|---|
| 确认「是否符合**已有**判据」 | **脚本** | 判据已知且确定；让 AI 读一遍等于重新执行一遍已知判据——**纯浪费，且结果不如脚本稳定** |
| 发现「**现有判据没覆盖**的问题」 | **AI** | 需要理解、联想、跨领域比对；脚本只会回答它被写去回答的问题 |
| 建立接手所需的上下文 | **AI，但只读最小集** | 指针链已把范围限定为「一张卡 ± 一篇记录」；**全量读不是理解，是没有指针** |

### 7.1 正确形态：脚本压缩，AI 判断

```
脚本先跑  →  产出摘要与结论（状态 / 全量计数 / 红黄项）     零 token，且可留痕
AI 再读   →  只在摘要上做判断，按需下钻到具体文件            有理解，成本可控
```

**反模式**：让 AI 从零读完 `reports/` 全部篇文档来「了解项目」——
那既得不到判据的确定性（人眼查不出整行截断），又付出了全量上下文。

### 7.2 什么时候**必须**让 AI 读原文

- 要判定**语义**（交接内容是否真实、要点是否覆盖关键信息）——脚本只能证「写了」，不能证「做对了」；
- 要**跨记录找模式**（同一类问题反复出现、命名渐次漂移）——这是联想，不是检索；
- 要**形成以后能复用的判断**（架构该怎么调、哪块该拆）——这是理解的收益，值得付上下文的成本。

> **一句话**：**脚本负责「有没有据可查」，AI 负责「有没有道理」。**
> 前者交给机器是省钱，后者交给人是省错。
