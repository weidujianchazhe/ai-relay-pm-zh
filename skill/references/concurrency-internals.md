# 并发控制 · 实现内部（Concurrency Internals）

> **何时读**：改并发相关代码 / 做并发与故障注入审计 / 需要判断「这条保证到底怎么来的」时。
> **不是使用者必读**——只想知道「规矩怎么写」的读者看 `concurrency.md` 就够了（分工见该文件顶部的分层阅读指引）。
> **定位**：本文件存**实现与理由**；规矩与保证等级在 `concurrency.md`。**两边不复制内容**——这里说怎么做，那里说是什么。

### 1. 三个层级——**别把 CAS 当事务**

这三件事常被混为一谈，混了就会以为「整个操作不会产生半成品」。**它们不是一回事**：

| 层 | 保证什么 | 本包状态 |
|---|---|---|
| **L1 Atomic Write** | **一个文件**：读到的要么旧全文、要么新全文 | 已做（临时文件 + 原子替换） |
| **L2 CAS** | **前置状态没变**才允许写（否则拒绝 + 冲突文件） | 已做（共享写原语） |
| **L3 Transaction** | **多个文件**：全部成功或全部回滚 | **不做**（见下） |

**L3 为什么不做**：跨文件事务需要日志或两阶段提交，而本作品是**文件 + 脚本**、没有常驻协调者；
硬做出来的半吊子事务，比明说「不是事务」更危险。本包改为**把每个多文件端点的语义写清楚**——
查 `python scripts/closeout.py . api` 的**原子性列**：

| 原子性 | 含义 | 端点 |
|---|---|---|
| `atomic` | 单文件 CAS，不会半成品 | `claim` · `release` |
| `best-effort` | **多文件，不是事务**：可能部分成功，重跑可收敛 | `index-add` · `archive-reports` · `reviews-archive` · `card-archive` · `design-archive` |
| `new-file` | 只建新文件，无竞争 | `new-record` · `new-card` |

> **失败后的收敛**：冷区先写成功、热区冲突时，**跑 `closeout.py repair` 即可幂等补齐**（不必人工对齐）；
> 归档类操作用「目标同名则跳过」，因此重跑不会重复移动、也不会覆盖。**这叫可收敛，不叫事务。**
> 三类残留各有补偿：**索引冷热差集 → 补**、**指向悬空 → 改指**、**半成品临时文件 → 清理**，
> 全部由 `closeout.py repair` 完成，**可重放、幂等**（跑第二遍报「无需修复」）。

### 2. 唯一共享写原语（SharedWrite）

**所有对共享文件（REVIEWS / INDEX / STATE / MAP / 两份冷区）的写，都必须走 `scripts/lease.py` 的原语**：

| 原语 | 用途 |
|---|---|
| `lease.write_cas(path, text, expected)` | 底层：前置哈希不符即拒绝 |
| `lease.shared_append(root, path, line)` | 追加一行（CAS） |
| `lease.shared_rewrite(root, path, new, base)` | 重写整文件（CAS） |


### 2.1 实现与边界（**check-before-write 不是 CAS**）

曾经写成「读 → 比对 → 写固定名 tmp → replace」，那严格来说只是 **optimistic check-before-write**：

| 曾经的做法 | 实测后果 |
|---|---|
固定临时名 `path + ".tmp"`，所有并发写者共用 | **互相覆盖**；replace 时对方已移走 → `FileNotFoundError` **外抛**；内容错位；**假成功**（返回成功但最终状态是别人的） |
比对与写入之间有窗口 | 两个写者都读到同一 expected、都通过比对、先后 replace → **lost update**（7 个报成功，只落 3 条） |

**现在的做法（三步都在临界区内）**：

1. **取锁**：`os.open(lock, O_CREAT|O_RDWR)` 打开**常驻锁文件**，再用**操作系统建议锁**
   （`fcntl.flock` / `msvcrt.locking`，非阻塞）取得所有权——这是本层唯一的、操作系统**原子原语**。
   不用「先判断存在再创建」，因为那本身就是 check-then-act（**用一个竞态修另一个竞态是修不好的**）；
2. **锁内比对**：读到的前置哈希与 expected 不符 → 明确失败（不写）；
3. **唯一临时名**（进程号 + 随机）+ `os.replace` + **写后回读校验**：磁盘上的内容必须是「我们写的那份」，
   否则返回失败——**调用方拿到的永远是「成功」或「明确失败」，不会是一个堆栈**。

**并发不变式（可执行、可测）**：N 个写者同时提交 → **最多一个成功，其余明确失败**；
**成功者所写的内容必须出现在最终文件里**；**不丢写**；**不出现返回成功却状态非本写者**。

#### 2.2 锁的唯一当前模型（CURRENT）

```text
persistent lock file  +  fd  +  OS advisory lock   →   ownership
release = unlock + close        （**不删锁文件**）
lock file ≠ ownership
```

| 层 | 机制 | 性质 |
|---|---|---|
| **主**（唯一层） | `os.open` + **操作系统建议锁**（Windows `msvcrt.locking` / POSIX `fcntl.flock`，非阻塞） | **暂停安全 + 死亡安全** |
| **不支持建议锁** | **明确失败，不降级**（`acquire_lock` 返回 None + 说明） | 降级给出的是**兑现不了**的保证 |

必须区分**两种故障模型**——历史 bug 的根因就是把它们混成一种：

| 模型 | 现象 | 正确处置 |
|---|---|---|
| **崩溃** | 进程死了 | 锁**自动释放**，新写者立即接管（否则工作区被永久堵死） |
| **暂停** | 进程活着但不执行 | 锁**仍属于它**，新写者必须**等或明确失败**——**绝不能接管** |

配合的两处协议细节：

1. **写前 + 写后各问一次「还是我的吗」**（`verify_lock`）：**只看 fd 上的 OS 建议锁是否还活着**。
   Windows 的字节范围锁是**强制**的，另开句柄读锁文件会 `PermissionError`，那样会把自己的锁误判成易主。
   （实测教训：曾因此让 10 个用例挂 8 个。）
2. **放锁不删锁文件**（`release = unlock + close`）。本项由 `concurrency_matrix` 的 **I10 / I11** 与 **I12** 断言。

> **CURRENT 读者到此即可完整理解当前锁模型**——以下为历史归档，可整节跳过。

#### 2.3 HISTORICAL / REMOVED（仅解释为什么删除）

**已删除的四件设计**（保留说明，是为了让下一位维护者**不会**再把它们当成当前机制）：

| 已移除设计 | 当年做法 | 为什么删除 |
|---|---|---|
| **EXCL fallback** | 不支持建议锁时改用 `O_CREAT\|O_EXCL` 造锁文件 | 给出的是**兑现不了**的互斥保证——**明确失败好过假装受保护** |
| **lock-age takeover（锁龄抢占）** | 锁龄超过 `LOCK_STALE` 即抢占（时序见下） | **按锁龄抢占只对「崩溃」成立，对「暂停」就是错的** |
| **rename takeover** | rename 抢占 + `epoch` 继承 | 需要「锁龄抢占 + epoch 继承 + 又一次 rename 竞态」——属**加机制**而非删机制 |
| **token/epoch 充当 ownership 判定** | 靠锁文件里的 `token`/`epoch` 判断「是不是我的 / 第几代」 | ownership 的**唯一权威是 fd 上的 OS 建议锁**；`token/epoch` 现仅作**代数记录与排障信息** |

**（已移除）锁龄抢占当年的时序**——它同时暴露了上表第二条：

```text
（已移除的旧模型）A 取锁 → A 被挂起（进程未死）→ 锁龄超过 LOCK_STALE → B 删除锁并取
                  → A 恢复后继续写，覆盖 B → A 在 finally 里删除 B 的锁 → C 也能进临界区
```

**当前实现已整体删除该模型**（连 `LOCK_STALE` 常量一起）。**放锁也不再有 `unlink`**：原实现**无条件 `unlink`**
会删掉抢占者的锁 → 第三个写者可直接进入（互斥被破坏）；该做法已随 `unlink` 一起移除——`token/epoch` 也因此不再参与放锁判定。

**被 Windows 教出来的两个实现细节**（都踩过）：

- Windows 的 `msvcrt` 锁是**强制**的：另开句柄读锁文件会 `PermissionError`——所以 os-lock 模式下**不能**用「再读一次锁文件」验归属，否则会把自家锁误判成已易主（实测：10 个用例挂 8 个）；
- Windows 上**文件还开着时 `unlink` 会失败**——放锁顺序必须是「判归属 → 解锁并关闭 fd → 再删文件」，否则锁文件永远清不掉。

**边界声明（更新后）**：

| 场景 | 保证 |
|---|---|
本机文件系统 + 支持建议锁 | **真互斥，且暂停安全**（I9） |
本机文件系统但**不支持建议锁**（含 NFS / SMB / 部分容器卷） | **明确失败，不降级**——降级会给出兑现不了的保证（不存在 EXCL/stale 退化路径） |
网络文件系统（NFS / SMB） | 建议锁语义不保证 → **按「不支持」处理：明确失败，不降级** |
跨机器同时写同一目录 | **不在保证范围内**（前提是「一个工作区一份本地文件系统」） |
绕过入口直接改文件 | **不受任何保护**，只能被漂移检测抓到 |
持锁进程崩溃 | OS 释放锁 → 新写者立刻接管；残留锁文件**不再阻塞**（只是垃圾，`sweep_temp` 可清） |

> **本节最重要的一句**：**把所有写收进一个「CAS 函数」≠ 系统获得了 CAS 语义**。
> 收进函数解决的是**写路径统一**（第 10 节守的那件事）；
> 而**线性化**（同一时刻只有一个写者的效果）必须由**操作系统级原子原语**提供——这正是上面第 1 步的作用。
**为什么必须收拢**：曾经存在多条直接 `tmp + os.replace` 的写路径（`audit_all` / `lang_gates` / `stamp` / `setup` / 归档流程），
它们**没有 CAS**——协议说「共享文件写前比对哈希」，实现却直接替换，两个 Agent 同时写就会**丢写**（经典 lost update）。
收拢后由 `gen_views.py` **第 10 节**机检：谁写了共享文件、用的是不是原语，**漏登记的写者当场报红**。


#### 2.3 层界：`locks.py` 与 `lease.py`

**为什么拆**：把五类职责（锁取放 / CAS 写入 / 租约 fencing / 崩溃恢复 / 清理）塞进 `lease.py` 一个模块，
每次审计都在它里面再加一层——那是「往屎山走」的信号。故按**层界**拆开：

| 文件 | 职责 | 谁用 |
|---|---|---|
| `scripts/locks.py` | **互斥的唯一物理实现**：OS 建议锁 / 平台分支 / 崩溃与暂停语义 / 锁归属 | 只被 `lease.py` 与业务原语调用 |
| `scripts/lease.py` | 租约与 fencing + 写入原语（CAS / append / rewrite） | `closeout.py` · `check_closeout.py` |

**业务侧的规矩（[强制]）**：只经 `lease.exclusive_resource(path)` 进入临界区，
**不要 import `acquire_lock` / `release_lock` / `verify_lock`**——那些是层内件。
平台细节（`flock` / `msvcrt` / `O_EXCL` / `epoch` / `inode` / `fd` / unlink）**只允许出现在 `locks.py`**。

**业务层还有一处** check-then-act：`claim()` 若写成「guard 读状态 → read 读内容 → write_cas 再写」三个时刻，
两个进程都能读到「无租约」再各自写入（并发矩阵 I3 实测两个都成功）。现在整段收进 `exclusive_resource(card)` 一个临界区。
### 3. Fencing：租约过期后的「僵尸写者」

**只比 owner 是不够的**。场景：A 认领（令牌 1）→ 过期 → B 抢占（令牌 2）→ 此时 A 的旧进程仍在写。
光看 owner，可能因轮转又落到 A 名下而放行；而那次写基于**过期状态**。

因此照搬分布式系统的 **fencing token**：每次认领令牌**自增、永不回退**；写入时带上自己的令牌，
**旧令牌 < 当前令牌 → 拒绝**（并生成冲突文件）。

```
python closeout.py <根> claim EN0007 --ai win-xxxx      → 回显：fencing 令牌=3
python closeout.py <根> card-archive EN0007.md --ai win-xxxx --token 3
  若当前令牌已是 4 → 拒绝：「租约令牌过期（你的 3 < 当前 4）」
```
**判定是「严格相等」**：`mine != current` → 拒绝，并区分两种情形——
`mine < current` 报「令牌过期」（僵尸写者），`mine > current` 报「令牌不存在」。
**不接受比当前更大的令牌**：早先写成 `mine < current` 才拒，于是伪造一个 `token=1001` 就能通过——
那是「防旧令牌」，不是「验证令牌」。
**它仍然是 opt-in**（这是有意的设计边界）：不带 `--token` 时不检查——便于存量工作区平滑迁移，
但**也就等于放弃这层防护**。真正多 Agent / 长生命周期场景应把它设为**必填**（届时是一条协议变更）。
**诚实的边界**：它只保护「经由入口的写」；绕过入口直接改文件，依旧只能靠漂移检测**事后**发现。
