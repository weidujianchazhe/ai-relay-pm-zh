# 协作模式与角色（Collaboration）

> **何时读**：要开多角色协作、要上设计卡、或要判定"谁有权做什么"时。
> **设计卡的完整规则不在这里**——见 `references/design.md`；本文件只留协作视角。
> ⚠ **默认全部关闭**。它们是**能力开关**，不是必选复杂度——单人/单 AI 场景直接跳过本文件。
> 开关位置：`config/defaults.yml` 的 `collaboration.*`（实例值在 MAP 规则段）。

---

## 1. 四档工作形态（按需升级）

| 形态 | 文件集 | 角色与检查 | 何时升档 |
|---|---|---|---|
| **card** | **一个卡片文件**（无工作区、无索引、无快照） | 无；靠人读卡 | 出现第二个写者 / 流水超过一屏 / 需要全局视图 → 升 light |
| **light** | 任务卡、**reports**（交接记录）、索引（热区 + 冷区＝archives/）、**designs**（按需） | 执行 AI；**提交流程三项**（记录 / 卡 / 索引）＋ ID 与路径门禁 | 需要全局视图（STATE）、多线并行或设计批准时升 standard |
| **standard** | light + **MAP**、**STATE**、**REVIEWS** | 执行 AI + 审计 AI；**提交流程四项**（多一项快照）、字段级更新、版本/归档检查 | 需要多人协作、跨分支或设计评审时升 coordination |
| **coordination** | standard + 设计卡、冲突文件、权限/事件证明 | 管理者分配 owner；CAS/原子写、冲突审计、批准门禁 | 风险下降且管理者明确批准后可降级 |

**升级即扩集，历史不回写。** 降级同理。

> **形态判定在第一次对话完成**（问句见 `references/onboarding.md` §1）。
> **从严到宽**：先按能跑的最小形态起步，发现不够再升——反过来先建全套再降级只会留下无人维护的空档案。
>
> **默认值**：`light`（见 `config/defaults.yml`）。**大多数单 AI 项目终身不需要升档**——
> 实测：源文件与测试文件合计逾百的项目，全程 `light` 即可运转。
> `card` 档不写 MAP（它没有 MAP），因此不进模式配置——它是**形态**，不是配置项。

## 2. 角色权限矩阵（roles — 默认关闭）

| 角色 | 允许 | 禁止 |
|---|---|---|
| **执行 AI** | 认领自己的任务卡、写自己的 reports/STATE 条目、提出设计卡 | 批准设计、覆盖他人 owner 文件、删除/移动档案 |
| **审计 AI** | 只读检查、生成 `[问题]`/`[待核]` 报告 | 修改业务记录、替代管理者裁决 |
| **管理者 / 裁决者** | 批准设计、分配 owner、裁决冲突/废弃、执行归档 | 无凭证改写历史 |
| **恢复 AI** | 只读生成候选与证明、经确认写恢复草稿 | 无确认覆盖正式文件 |

**启用代价**：需要真正的**多主体在场**（不同 AI 会话 / 不同人）。
**实测教训**：当执行者与复核者是**同一个 AI 标识**时，四角色矩阵形同虚设——
实测：归档卡中明文写「自复核」者占一定比例，而全部记录中「打回」为零。
**判据**：如果复核报告的署名与被复核报告相同，角色分离就**没有发生**。

## 3. 稳定标识（stable IDs — 默认关闭）

| ID | 格式 | 语义 |
|---|---|---|
| 任务标识 | `TASK-YYYYMMDD-<6位大写 base32>` | 任务卡创建后**永久不变**；文件名可改，引用只能用 ID |
| 事件标识 | `EVT-YYYYMMDD-<8位大写 base32>` | 每次交接、归档、恢复、冲突和批准事件唯一；**重试也产生新 ID** |
| 设计标识 | `DSN-YYYYMMDD-<6位大写 base32>` | 设计卡唯一 |

**启用代价**：每次写卡都要生成并记录 ID——属**高频写路径成本**。
**建议**：仅在需要跨系统引用（如与外部 issue tracker 对接）时启用；
否则用 `XX0000` 分支码 + 文件名即可（见 `references/artifacts.md` §2 冻结区）。

## 4. 设计（design — 默认关闭）

**全量规则已移入独立功能域文件：`references/design.md`**——两件套（详述 + 蓝图）/ 成本纪律 / 生命周期与批准门禁 / 设计区与归档。

本文件只留与本域相关的两条：

**批准门禁**：**只有「已批准」的设计卡才能生成执行任务卡**（执行卡回填 `DESIGN-ID`）；批准、拒绝、废弃均写事件标识。

**何时启用**：设计本身是交付物的一部分（对外接口、跨团队契约、需要留痕的架构决策）。
**何时不启用**：实现已由现成规范覆盖时——此时「设计」就是规范条款，再建卡是重复。

## 5. 上下文切片（task brief — 派发约定）

派发给执行者时，**不派全文**，只派**最小必要的上下文切片**：

```
【书写要求】难度 D? · 视觉 V? · 本卡按代码质量门禁执行（速查卡附后 / 标杆文件见下）
【规范速查卡】不超过 20 行的强制条款清单（按卡裁剪，不附全文）——守最小注入
【标杆文件】本项目的风格参照文件路径（风格是抄会的，不是读规范会的）
【验收口径】按卡填写
```

**目的**：把"执行者必须读的东西"压到最小。**派全文＝把规范包的成本转嫁给每一个执行者。**

| 契约 | 谁在消费 |

| `TASK-ID / EVENT-ID / DESIGN-ID` 格式 | ID 锚校验（启用时） |
| 设计卡状态机五态 | 批准门禁校验（启用时）——其余设计契约见 `references/design.md` §6 |
| 派发切片四段结构 | 任务简报格式（启用时） |
