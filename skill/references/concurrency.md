# 并发控制（Concurrency）

> **何时读**：多 AI / 多会话可能同时写同一工作区时。
> **核心命题**：文档层做不到实时监督——但**脚本能拒绝的，就不要只写进约定**。
>
> **分层阅读（按需停，别整篇读）**：
> · 只想**知道规矩怎么写** → 读 §0 + 下面「三条用法」（约 1.6k 字符）▸ **大多数人到这里就够**
> · 想知道**能保证什么、什么不保证** → 再加 §0.4 保证等级表（约 1.4k 字符）
> · 要**改并发代码 / 做审计** → 再看 `references/concurrency-internals.md`（实现与理由，约 3.5k 字符）

## 0. 两级强制 + 一级检测（先读这一节）

**"请遵守单写者"是协议，不是强制。** 本包把能变成强制的那部分变成了强制：

| 层 | 保护对象 | 机制 | 谁执行 |
|---|---|---|---|
| **任务级** | 一张任务卡 | **租约**：`owner + lease + claimed_at + expires_at`（落在既有的「并发元数据」行里） | `closeout.py claim / release` 写；写入前 `lease.guard()` 校验 |
| **文件级** | INDEX / 冷区 / REVIEWS 等共享文件 | **CAS**：写前比对 `NORMALIZED-SHA256`，内容被别人改过就**拒绝写入** | `closeout.py` 的 `_cas_write()` |
| **检测级** | 绕过脚本的直接编辑 | 卡上记的哈希与文件实际内容不一致 → 报 `[问题]` + 生成冲突文件 | `check_closeout.py` §6 |

```
A: claim EN0007 --ai win-aaaa        → owner=win-aaaa, expires=+30min, revision+1
B: claim EN0007 --ai win-bbbb        → **拒绝**（租约属 A）；--steal 并写理由才可抢占（留痕）
B: card-archive EN0007 --ai win-bbbb → **拒绝**（该卡由 A 持有）
租约到期 → B 可直接 claim（不必等谁批准）
有人绕过脚本手改卡 → check_closeout 报 [问题] + CONFLICT_<ID>_<ts>.md
```
**写入收口（[强制]，分两层说，别混）**：

| 写什么 | 唯一入口 |
|---|---|
| **业务写**：任务卡 / 索引 / 归档 / 建卡 | **`scripts/closeout.py` 的子命令** |
| **共享文件**（REVIEWS / INDEX / STATE / MAP / 两份冷区） | **一律经 `scripts/lease.py` 的原语**（`write_cas` / `shared_append` / `shared_rewrite`）——留痕类命令（`stamp.py --append` / `lang_gates.py record` / `audit_all.py` / `setup.py`）也**不例外** |

> 为什么分两层：**业务写**有语义（认领、编号、归档），走 `closeout` 才有一致的校验与审计；
> 而**留痕**是各工具的职责（机器戳、语言门禁、全盘核查各要写一行），硬塞进 closeout 反而添耦合。
> 两者共同的底线是**经原语写入**——原语里才有 CAS 与锁；谁是什么角色，在第 10 节的登记表里一目了然。

直接编辑这些都算**绕过**，由检测层按哈希漂移抓（见 §0 表第三行）。

> 这一条是折中方案的落点：**要 API 的语义，不要 API 的常驻成本**。
> 端点契约可以随时查：`python scripts/closeout.py . api`（**从实现导出**，不是手抄的第二份副本）。

**边界（必须与上面一起读）**：本层强制的是**经由脚本的写入**。
有人用编辑器直接改文件，脚本拦不住——**那种情况由检测层兜底：拦不住的，也一定看得见。**
这与本包「事后可审计」的定位一致：不承诺防呆，承诺**不守规矩必留痕**。



### 0.1–0.3 你要知道的三条用法（**实现与理由已移出** → `references/concurrency-internals.md`）

**① 共享文件的写必须走 `scripts/lease.py` 的原语**（`write_cas` / `shared_append` / `shared_rewrite`），
**不许自己 `tmp + os.replace`**。为什么、以及它挡住过什么，见 internals §2。

**② 多文件操作不是事务**：`index-add` / `archive-reports` / `reviews-archive` / 归档类**可能部分成功**。
每个端点的原子性看 `python scripts/closeout.py . api` 的**原子性列**（那里是唯一权威，别抄一份）。
**半事务不必人工对齐——跑 `python scripts/closeout.py repair` 即可幂等补齐**
（索引冷热差集→补 · 指向悬空→改指 · 半成品临时文件→清理；跑第二遍报「无需修复」）。

**③ fencing 令牌**：`claim` 会回显「fencing 令牌=N」，**后续写入带上 `--token N` 才启用这层防护**
（挡住「租约已被抢占、旧进程仍在写」的僵尸写者）。**不带 token 就不检查**——那等于放弃这层。
判定是**严格相等**：旧令牌与伪造的更大令牌都会被拒。

### 0.4 保证等级表（**每个操作到底承诺什么**）

五档定义：**强保证**（任何情况都成立，有可执行用例）· **条件保证**（满足明确前提才成立）·
**最终一致**（可能短暂不一致，但可收敛）· **仅事后检测**（发生时挡不住，事后一定能发现）· **完全不保证**（明确不承诺）。

| 操作 | 等级 | 前提 / 靠什么 |
|---|---|---|
| 并发 `write_cas`（同一前置） | **强保证**\* | 至多一个成功、其余明确失败、无异常外抛、成功者所写必在文件里（I1） |
| 并发 `shared_append` | **强保证**\* | 成功数 == 落盘行数（锁内读—改—写，追加可交换）（I2） |
| 并发 `claim` | **强保证**\* | 恰好一个成功，且 owner 与成功者一致（I3） |
| **暂停模型**（持有者被挂起，进程未死） | **强保证**\* | 锁跟着 fd 走：挂起不释放 → 新写者**不得接管**，只能等或明确失败（I9）。退化模式下退为**条件保证** |
| fencing 令牌（带 `--token`） | **条件保证** | 前提：**带令牌**且严格等于当前值；旧令牌与更大令牌都拒（I4） |
| fencing 令牌（不带） | **条件保证** | 前提：调用方自觉带令牌；不带＝**放弃这层防护**（opt-in 边界） |
| **崩溃模型**（持有者进程死亡） | **强保证**\* | 操作系统释放锁 → 新写者**立即接管，不依赖锁龄**（C2）；残留锁文件不再阻塞，`sweep_temp` 可清（C1/I5） |
| `index-add`（冷区 + 热区） | **最终一致** | 单文件各为 CAS；跨文件不是事务，但半事务可由 `closeout.py repair` **幂等补偿**（前提：跑它） |
| `card-archive` / `design-archive` | **条件保证** | 单文件在锁内（守卫 + 移动同一临界区）；多文件移动非事务 |
| `archive-reports` | **条件保证** | 移动时同名跳过 + 索引 CAS；整体 best-effort |
| `closeout.py repair`（半事务补偿） | **最终一致** | 幂等可重放：索引冷热差集补全 · 指向修正 · 崩溃残留清理；跑第二遍报「无需修复」（C5） |
| 旧持有者放锁时误删新锁 | **强保证**\* | 只删归属仍属于自己的锁；他人锁被保住（I10）。**退化模式下**才需要靠 token/epoch 判断 |
| 证据（provenance）真伪 | **仅事后检测** | 只能提高伪造成本（`verified=`），**不能证明不可伪造** |
| 跨机器 / 网络文件系统互斥 | **完全不保证** | 前提是「一个工作区一份**本地**文件系统」 |
| **不支持建议锁的文件系统** | **明确失败，不降级** | `acquire_lock` 直接返回失败并说明原因——**不存在 EXCL/stale 退化路径**：降级会给出兑现不了的保证 |
| 多文件「全或无」 | **完全不保证** | 无事务层（§0.1）；只承诺可收敛 |

**怎么复现这张表**：`python scripts/concurrency_matrix.py`（I1–I10）· `python scripts/crash_matrix.py`（C1–C5）。

\* **带 \* 的「强保证」有一个共同前提**：平台支持操作系统建议锁（Windows `msvcrt` / POSIX `fcntl`）。
**不支持时明确失败，不降级**（不存在 EXCL/stale 退化路径）：`acquire_lock` 返回失败并说明原因——降级会给出兑现不了的保证。
> 这张表的意义：**把「代码里声称的保证」与「实际能证明的保证」分开**——
> 表里每一行要么有可执行用例，要么明确写着「不保证」。**没有第三种含糊状态。**

## 1. 单写者原则（single-writer principle）

**每个文件在同一时刻只能有一个声明的 owner。** 非 owner 不得覆盖，只能：

```
生成冲突文件  CONFLICT_<ID>_<timestamp>.md
```

并交管理者裁决。**时间戳仅作辅证**，不作裁决依据（见 §4 反激励原则）。

---

## 2. 写入协议（write protocol）

```
① 写前读（read-before-write）
     覆盖写 STATE / 任务卡、追加写索引之前，先读最新内容
② 记录元数据
     每次写记录 revision、规范化内容的 SHA-256、写者 ID
③ 原子写或 CAS
     优先「临时文件 + 原子 rename」
     不具备原子 rename 时用 compare-and-swap（提交前再次比对 revision/hash）
④ 写后验（verify-after-write）
     重读并核对 revision/hash 是否与预期一致
```

**为什么要有 ③**：平台写入可能是非原子的；中断会留下半截文件。

**实现状态**：③ 已由 `scripts/closeout.py` 的 `_cas_write()` 落实（共享文件写前比对哈希，不一致即拒绝并生成冲突文件）；
② 的三元组写在卡的「并发元数据」行里。**CAS 只在"经由脚本"的路径上生效**——绕过脚本的改动由 §0 的检测层抓。

---

## 3. 字段级更新（field-level update）

并行提交时，**STATE 只更新自己任务的条目与人读区**，其余原样保留。**禁止整文件盲覆盖**。

任务卡同理：只写自己认领的卡。

---

## 4. 冲突裁决（conflict resolution）

- 裁决权归 **MAP 规则段登记的裁决者**；用户保留终裁
- **跨分支冲突不比编号、不以时间戳裁决**——留痕交管理者，时间戳仅辅证
- **反激励原则**：任何裁决规则**不得给伪造留收益**。
  教训：「跨分支以时间戳后写为准」＝「谁伪造时间戳谁赢」——**裁判规则作弊有奖即是漏洞**。

---

## 5. 编号并发（ID allocation）

- **编号三口径**：卡号（任务卡的稳定身份，建卡后不变）· 索引行号（登记序号，严格递增）· 交接号（记录内编号，取当前最大值 + 1）
  → **三者允许不同源，但必须各自唯一且可交叉引用**
- 并行时段**号段分配**：多路同时在飞时各自认领互不重叠的号段
- **撞号处理**：让位 + 留痕（后申报者顺延重编并在记录中写明）
- 时间戳 **不得**用作冲突裁决（见 §4）

---

## 6. 三个及以上 Agent 同时动同一个文件（处置顺序）

**先分流，再动手**——不同资源用不同办法，混着处理必然踩掉别人的活：

| 情形 | 处置 |
|---|---|
| 同一张**任务卡** | 任务级租约：`claim` 一次，其余人写前被 `guard()` 拒绝；要让出先 `release`，忘了就等租约到期 |
| 同一份**共享文件**（INDEX / 冷区 / REVIEWS） | CAS 写：读之后、写之前内容变了就**拒绝写入**并生成冲突文件——**不要让后写者覆盖掉别人的那一行** |
| **两条并行支线各自写索引** | 号段分配（§5）：各自认领互不重叠的号段；撞号者让位 + 留痕 |
| 同一**源码文件**（真正的工作冲突） | 不在本包职责内——交给版本控制（分支 / 合并）；本包只保证**记录里写清谁改了它**（「改动点」块 + commit 哈希） |
| 想改别人的卡，而对方已离线 | **等租约到期**，或 `--steal` 并写明理由（留痕）；**不得静默覆盖** |

**顺序纪律**：先冷区后热区（索引）· 先记录后卡（提交）· 先写成功再移动（归档）。
**任何一步失败都不许接着往下做**——半途状态比没做更难查。

---

## 7. 写锁的边界（诚实声明）

**本包实际使用的是操作系统建议锁**（Windows `msvcrt.locking` / POSIX `fcntl.flock`，非阻塞）——见 `concurrency-internals.md` §2。
它跟着 fd 走：**进程暂停不释放，进程死亡由 OS 释放**（这正是保证表里那两条强保证的来源）。
但：

- 锁**只在本机有效**，跨机器/跨平台不成立
- 取锁超时后**不得无限等待**——**明确失败 + 留痕**，让使用者知道这次没写成；
  **绝不降级为「无锁写」**：那会在他人持锁时直接写坏共享文件（丢更新），是并发损坏而不是"保住改动"
- 因此锁是**加固**，不是**保证**；真正的保证来自 §1 单写者原则与 §2 写后验
