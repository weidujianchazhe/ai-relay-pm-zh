AI 协作项目管理技能

让 AI 持续参与一个真实的软件工程项目，而不是每次重新认识项目。

一句话

它是一套语言无关的软件工程管理协议 + 一组确定性门禁脚本：把项目的状态、设计、任务、实现、验证、交接串成一条可追溯的链；人手离开、AI 换人、会话中断之后，下一个接手者能只读所需接着干。

不绑定平台，不依赖任何服务，脚本只依赖 Python 3 标准库。

它不是什么（先划边界）

不是 C++ / 算法 / UI 专家　不是 自动监督 AI 的 Agent　不是 替管理者裁决的系统　不是 运行时常驻守护

它负责的是：让这些专业能力产生的工程结果，能够被持续管理。

诚实声明：允许能力不足，但不允许把不足伪装成有能力——所有"没做 / 没接 / 没证据"都会显式写成 [待核]，而不是"看起来通过"。

我能用它做什么

按「你遇到的问题 → 它提供的能力」看最快。

问题 → 能力

你遇到的它提供的
AI 换了 / 会话断了 / 几天后回来项目接手与上下文恢复（读得少、接得上）
多个 AI 同时工作统一任务、状态、交接与留痕
项目越大，AI 越难读全接手成本控制：按需要读取的内容量计算，而不是按项目文件数量计算（AI 的实际接手成本更接近需要读取的文本量）
设计想清楚了，执行时却忘了设计 → 任务 → 实现 的结构追踪
AI 说"已完成"但无法确认门禁 · 证据 · 独立审计（先证明门禁会红）
管理越来越乱七种工程对象：MAP / STATE / SKELETON / DESIGN / TASK / AUDIT / ARCHIVE
只想轻量用四个子能力可独立使用
不同语言、不同专业能力管理层与专业能力解耦（语言只决定适配层）

四个子能力，可从任意一个开始

子能力一句话单独用
① 项目地图 MAP项目在哪、代码在哪、按什么规则运转✅ 一个文件即可
② 任务卡 TASK现在做什么、谁在做、怎么算做完✅ 单卡可用
③ 设计管理 DESIGN把已论证的工程意图固化为可对照的基线✅ 两件套可用
④ 代码质量护栏只保下限（可机检判据），不封上限✅ 脚本可单独拷贝
每个子能力都能单独用；但组合起来才有"接手成本不随项目增长"的效果。需要多少，启用多少。

它解决什么问题

核心命题：项目可以复杂沉重，AI 接手只读所需。

四类真实问题

问题它的做法
重复解释项目把状态外置成文件（MAP / STATE / 记录），而不是塞在对话历史里
交接靠嘴说交接有固定块与机器戳；下一手按指针读，不重读全部
"完成了"无法验证退出码即结论 + 变异自检（先证明门禁会红）+ 独立复核
设计与实现脱节设计先于执行；任务回链 DESIGN-ID；结构 ↔ 设计可追溯

适用 / 不适用（诚实版）

适用

  • 需要长期、多轮、可能换 AI 接手的项目
  • 需要留下"为什么这么做"的工程项目
  • 多人 / 多会话共享同一份工程状态

不适用

  • 单轮问答、写一段代码就走
  • 纯技术咨询、与项目管理无关
  • 已有完整体系、本次只做业务开发
单独使用任一子能力时会缺哪些门禁都有明确声明——见第 8 页与包内 MANIFEST.md 的「子能力与最小集」。

它是怎么工作的

一句话：它如何让 AI 持续工作？按用户理解路径，七步。

① 项目先有地图

MAP：项目在哪、代码在哪、按什么规则运转。

② 现在真实的结构是什么

SKELETON：项目当前工程模型——总体架构、模块关系、主路径、设计落在哪。（同一份骨架两种阅读：HTML 给人、Markdown 给 AI）

③ 每项工作有任务

TASK：现在做什么、改哪里、怎么算做完。

④ 设计先于执行

DESIGN：已论证的工程意图——详述 .md + 蓝图 .blueprint.html。定稿才允许生成任务卡。

⑤ 每次工作产生交接状态

REPORT / INDEX / STATE：下一个接手者从哪里接着做。

⑥ 实现必须留下可验证结果

AUDIT / 门禁：由脚本与独立复核回答，不由"AI 说完成"回答。

⑦ 历史进入冷区

ARCHIVE：任务侧与设计侧分开归档，不干扰下一次接手，仍可追溯。

产品核心就是这条链：MAP → STATE → SKELETON → DESIGN → TASK → CODE → AUDIT → ARCHIVE
其中 CODE 是实际工程实现，不属于管理对象——七种工程对象（见第 6 页）负责管理它与其他工程状态之间的关系；所以这里有 8 个节点，而工程对象是 7 种。

从轻量到完整，怎么使用

从轻到完整：不确定就先小，需要再升级；升级是扩集，历史不回写。

四级形态

单卡              一份任务卡 / 一份 MAP / 一份设计两件套     ← 只用子能力
  ↓
轻量工作区        加 INDEX / STATE / 交接记录
  ↓
完整工程管理      加设计基线 / 审计 / 归档 / 门禁脚本
  ↓
多 AI 多会话协作   加单写者约束 / 机器戳 / 并发控制
它不要求你一上来就建几十个文件——形态定错是唯一需要重建的决定，所以技能会先问形态。

设计 · 任务 · 状态 · 审计怎么连接

v4.0 的工程认知模型：每个工程对象，都有它唯一的家。

七种工程对象

对象回答主要承载
MAP环境与规则MAP.md
STATE当前运行状态STATE.md
SKELETON项目当前工程模型designs/SKELETON.html + SKELETON.md
DESIGN工程意图与设计基线designs/<主题>.md + .blueprint.html
TASK执行计划tasks/*（回填 DESIGN-ID）
AUDIT对实际结果的独立验证门禁脚本 + 独立复核
ARCHIVE历史事实archives/（任务）· designs/archives/（设计）分开

四条容易忽略、但 v4.0 明确规定的规则

① 结构 ↔ 设计，双向可追溯

关系建在结构层：工程板块 / 模块 / 路径 ↔ SKELETON ↔ DESIGN-ID。不给每个代码文件绑 DESIGN-ID——那只会制造负担。

② 设计完成 ≠ 可以开工

定稿只是"可以进入实施分析"。开工前要能回答两句：这项工作在项目整体结构中的位置、实施依据什么结构。答不出就不开工，或退回设计。

③ 任务完成 ≠ 设计失效

任务全做完，设计可能仍是当前工程基线，继续作为对照依据。

④ 「暂不实施 · 基线保留」是合法状态

设计可以有效但不立即实施（未来规划 / 架构基线 / 设计库存）——不产生任务、也不归档。设计不是待办事项。

设计变更时，必须登记受影响结构与受影响任务并写 EVENT-ID——不得只改一个 Markdown。

它不是什么

这一页的意义：防止把它误认成"AI 自动项目管理 Agent"。

明确的非目标

它不做为什么
不实时监督 AI监督是脚本层的事（确定性函数）；文档层只保证事后可审计——不拦你，但你做了什么一定留痕
不做运行时守护不常驻、不挂进程；它是协议 + 可按需执行的脚本
不判语义机器判不了的（注释质量、结构合理性、边界完备）交人或模型，并明确标注为人检
不替人裁决冲突裁决归项目登记的裁决者；系统只保证过程留痕
不实现平台能力定时 / 可视化 / 报告强依赖平台：只给规范，不随包分发实现
不自研语言分析器语法 / 类型 / 编译 / 静态分析交给成熟工具（ESLint / clang-tidy / clippy…）；本包只做编排与判据

它承认自己的能力边界

  • 未接线的语言一律 [待核]——那是"不适用"，不是"不合格"
  • 没有证据的结论不允许是"通过"（数值 / 算法类尤其如此）
  • 脚本崩溃（退出码 3）与项目检查失败（退出码 1）是两种状态，不得混读
  • 工具没装 → 报 [待核] provider unavailable，技能不代装

深入设计：为什么它这样设计

读到这页，你已知道"是什么 / 能做什么 / 怎么用"；下面是"为什么"。

为什么门禁必须能被故意打红

一个永远返回 0 的脚本，和一条被删掉的检查，从输出上看不出区别。所以顺序固定：先证明门禁活着，再拿它判别人。

对应口号：能通过 ≠ 能变红。

为什么证据不能自报

锚的值必须由被审计者之外产生。姓名、自取的名字、自编短码都与声明同源，可任意填写；机器码、时钟、版本控制提交号与声明异源，才可作锚。

所以：人检标记只挂机器戳、不挂人名。

为什么存在强耦合（且不许随意解耦）

有些字段名、目录名、编号格式是机器契约——改名即破坏功能。它们看起来"只是几行"，实际是节点。

改动前必须回答六问（谁在读它、改后是否仍有等价路径、接手成本是否上升……）。

为什么不做这些（设计上的克制）

不做原因
不复制编译器能力重复造轮子只会制造新噪声
不把工具默认值当标准工具默认 → 候选证据 → 真实项目验证 → 才成为规则
不为"完整"增加机制判据：没有它，会不会导致某个工程职责无法可靠完成？答案若只是"更方便" → 记为未来想法，不做

自相矛盾的地方，它会自己报

四层载体契约（规范 → 模板 → 生成器 → 验证器）由机检守护：任一层偷偷退回旧载体，门禁直接变红。

同一事实穿过各层不得变形——这是它防"改了一半以为改完了"的方式。

开始使用

从一句话开始：告诉我你要做什么，技能会先判断形态，再决定建多少结构。

三种入口

你的情况怎么开始
新项目走初始化：定形态 → 建管理区 → 展开技能 → 跑结构校验
已经在做的项目走存量接入：轻量登记（不深挖历史）→ 渐进整理；首轮只做只读盘查，不作阻断
已经有管理区直接接手：读 MAP / STATE → 认领任务 → 按指针读所需
存量项目特别注意：先抽样 → 精度抽检 → 基线冻结为豁免，之后只对新改动启用阻断；否则等于"用新噪声替换旧噪声"。

能力边界（诚实清单）

  • 单用 MAP：缺任务流、缺交接、缺审计
  • 单用任务卡：缺索引、缺快照、缺提交门禁
  • 单用 code_metrics.py：阈值有脚本内兜底，但与 config 的逐键一致性失去机检
  • 脚本崩溃（3）≠ 项目检查失败（1）

这些边界不会因为你没读文档而消失——所以它们被写在最显眼的地方。
